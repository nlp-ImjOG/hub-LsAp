# 电商数据智能问答系统（ChatBI）项目设计文档

> 版本 V1.0

## 一、项目背景与现状分析

公司电商业务的日常经营高度依赖数据，但取数这件事长期依赖少数人。业务人员每天要回答的问题并不复杂：某个区域上个月的退货率是多少、某个品类的动销商品占比如何、某次促销带来的新客有没有达到预期。问题简单，取数过程却不简单——提需求、排队、等报表，等数据到手，业务节奏已经换了一轮。

现有 BI 工具并不缺能力，缺的是入口。它已完成数据源接入、报表配置、图表展示与定时推送，四个主题的几十张表也早已接入。真正卡住的是使用方式：工具的起点是“配置一张报表”，而不是“问一个问题”。会配报表的只有数据组和少数业务骨干，其余几十号人只能提交需求排队等待。

表 1  现状痛点与业务后果

| 痛点 | 具体表现 | 业务后果 |
| --- | --- | --- |
| 取数排期 | 临时取数需人工排期，中位等待 1 至 3 个工作日 | 促销复盘与库存调整错过窗口 |
| 使用门槛 | 能独立取数的人占比不足两成 | 数据能力被锁在少数人手上 |
| 口径不一 | 同一指标在不同报表与手工计算中取值不同 | 会议在对数而非决策 |
| 重复劳动 | 同类问题被反复提问、反复人工答复 | 数据组大量工时耗在重复取数 |
| 决策滞后 | 数据到位时业务动作已经结束 | 决策只能依赖经验 |

三点后果需要正视：取数排期常态化，数据从支撑决策退化为事后说明；口径各算各的，会议时间消耗在对数而不是决策上；决策滞后，等活动结束、库存压住，数据才到位。

结论与判断：问题不在工具能力，而在使用接口。把取数入口从“配置”换成“提问”，是本项目唯一的价值主张；若维持现状，数据团队会随业务规模线性膨胀，而业务侧的等待时间不会缩短。

## 二、问题定义与项目目标

把现状收敛为四条可检验的命题，是本项目立项的前提；命题不成立，项目就不该做。

P1 取数耗时：一次临时取数从提出到拿到结果的中位耗时为 1 至 3 个工作日。

P2 使用门槛：几十人的业务团队中，能独立完成取数、不经过他人的占比不足 20%。

P3 口径一致性：同一指标在现有报表与人工计算之间存在差异，且差异无法当场解释。

P4 可信度：现有自助工具在无法回答时倾向于给出看似合理的结果，使用者无从判断数字是否可信。

目标分为业务目标与技术目标，每条都必须可被验收，不接受“体验更好”“效率提升”这类表述。

表 2  目标与验收方式

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| B1 | 业务自助：无需排期即可取到本人负责范围内的数据 | 试点期自助提问占比 ≥ 70% |
| B2 | 取数效率：单次取数从工作日级降到分钟级 | 中位响应 ≤ 60 秒，P95 ≤ 3 分钟 |
| T1 | 生成准确：SQL 可执行且结果正确 | 评测集准确率 ≥ 70%（一期）、≥ 85%（二期） |
| T2 | 答不准明说：不确定时说明原因与建议 | 编造率 0，明说率 100% |
| T3 | 权限与审计：行级权限与脱敏强制执行 | 越权拦截率 100%，审计完整率 100% |

结论：P1、P2 成立，项目就具备立项价值；P4 决定项目能否上线。一个偶尔编造数字的系统，业务人员用两次就会弃用，不会给第三次机会。

## 三、产品定位与范围边界

一句话定位：面向业务人员的电商销售数据自助问答系统，用自然语言提问替代报表配置，直接返回数据表、可复核的 SQL 与一句话结论。

与现有 BI 的关系是长期替代，不是并存。并存的代价很明确：两套口径、两处维护、两份培训，用户遇到答不准时仍然退回旧工具，替换覆盖率永远上不去。因此从一期起，主指标就是存量报表的替换覆盖率，而不是新增一个查询入口。

### 3.1 做什么与明确不做

表 3  范围清单

| 类别 | 内容 | 说明 |
| --- | --- | --- |
| 做 | 自然语言提问、SQL 生成与结果表展示 | 覆盖订单、商品、用户、区域四主题，SQL 可复核 |
| 做 | schema 检索（轻量 RAG） | 按问题召回相关表与字段，控制外发内容 |
| 做 | few-shot 示例库 | 用已确认的正确问答对齐口径与写法 |
| 做 | 执行报错自动重试 | 错误信息回灌模型，限定重试次数 |
| 做 | 行级权限、字段脱敏、全量审计 | 在数据访问层强制执行，不依赖模型自觉 |
| 不做 | 语义层 / 指标中心 | 一期不背指标治理的包袱，靠检索与示例换启动速度 |
| 不做 | 私有化部署本地模型 | 只外发 schema 与问题，不额外投入算力 |
| 不做 | 明细业务数据外发 | 公网模型仅接收 schema、字段注释与用户问题 |
| 不做 | 多轮对话、自动图表、看板、导出 | 二期范围，一期只做单轮闭环 |

关于语义层与指标中心，需要单独说明：它不是不重要，而是时机不对。指标治理要求先把全公司口径统一并沉淀为资产，本身需要数月跨部门对齐；一期做它，等于用治理周期换启动速度，PoC 永远落不了地。本方案用 schema 检索保证“找得到表”，用 few-shot 示例保证“写得对”，用报错重试保证“改得回来”，把口径问题延后到二期以运营方式收敛。

结论：范围边界比功能清单更重要。一期只做单轮问答的最小闭环，任何超出闭环的需求都进二期清单，不在验证阶段讨论。

## 四、用户角色与典型场景

系统面向三类角色，权限差异体现在数据视野上，而不是功能菜单上。

表 4  角色职责与数据视野

| 角色 | 职责 | 数据视野 | 关键约束 |
| --- | --- | --- | --- |
| 业务人员 | 自助取数、日常经营分析 | 仅本人归属区域与负责品类 | 敏感字段默认脱敏 |
| 区域/部门管理者 | 区域汇总、横向对比、下属复核 | 所辖区域全量及下级汇总 | 不含个人敏感字段明文 |
| 系统管理员 | 账号权限维护、审计查阅、运营配置 | 全量 | 明文查看单独留痕 |

以下五个是真实会发生的提问，它们同时决定评测集的构成：

S1 “上个月华东区退货率最高的三个品类是什么，各自退货率多少？”

S2 “近 30 天新客首单金额按省份分布，客单价低于 50 元的省份有几个？”

S3 “双十一当天支付订单中使用了优惠券的占比，和去年比是升还是降？”

S4 “我负责的三个品类里，本周动销商品数比上周变化最大的是哪一个？”

S5 “上季度各区域 GMV 和退货率放在一起看，哪些区域是量大但退货也高的？”

这些问题的共同特征值得注意：全部是聚合与对比；全部带有时间范围与维度约束；全部能用一句 SQL 表达；全部要求口径明确，例如退货率的分母是支付订单还是签收订单。这四点决定了检索的召回范围、示例的组织方式和评测集的标注口径。

结论：场景清单不是用来演示的，是用来定义验收的。评测集必须由业务人员按上述形态出题，而不是由技术团队自己编题。

## 五、总体方案概述

系统能力分四层，每层只做一件事，层间以明确契约衔接。

表 5  四层能力与职责

| 层次 | 一句话职责 | 关键机制 |
| --- | --- | --- |
| 交互层 | 承接提问、展示结果 | Streamlit 单页：结果表、SQL、结论三块并列 |
| 问答引擎层 | 把问题变成可执行 SQL | Agents SDK 编排：检索、示例、重试、置信判定 |
| 数据访问层 | 只读、按权限执行 SQL | FastMCP 工具层：权限注入、脱敏、超时、全量审计 |
| 运营治理层 | 让系统长期不退化 | 描述维护、示例增删、badcase 归因、评测回归 |

这个分层为什么能同时解决“门槛高”和“答不准”？门槛高是交互问题，交互层把入口从配置改成提问；答不准是工程问题，引擎层用三重机制收敛不确定性——检索保证看到正确的表，示例保证写成正确写法，重试保证错误能被修正，置信判定保证不确定时明说而非硬答。访问层把权限从“模型自觉”变成“系统强制”，这是内部系统能上线的前提。

需要强调的是，四层之间是契约关系而非调用关系：引擎层不直接连数据库，只调用 FastMCP 工具；访问层不理解自然语言，只接受带权限上下文的 SQL。这个边界让每层可独立测试，也便于二期替换前端。

结论：分层的价值不在图上好看，而在于不确定性被收敛在引擎层、安全性被收敛在访问层，两者可以分别验收。

## 六、实施路线

项目分三期推进，每期有独立目标、交付物与退出条件，未达退出条件不进入下一期。

表 6  三期实施路线

| 阶段 | 目标 | 交付物 | 退出条件 |
| --- | --- | --- | --- |
| 一期 PoC | 验证单轮问答闭环可行 | 提问到结果表与 SQL 全链路、100 题评测集 | 准确率 ≥ 70%，编造率 0 |
| 二期 试点 | 在真实业务中跑通并沉淀运营 | 多轮对话、自动图表、看板、导出、反馈纠错 | 自助占比 ≥ 70%，覆盖率 ≥ 30% |
| 三期 替代 BI | 覆盖存量报表，建立运营体系 | 完整行级权限、运营后台、存量报表迁移 | 覆盖率 ≥ 70%，运营稳定运行 |

为什么必须先做 PoC 而不是直接铺开？三个原因。第一，准确性是未知量，公网模型在电商 schema 上的准确率只能测出来、猜不出来；第二，评测集必须先于系统存在，没有一百道业务真题，后续所有“效果不错”都无法证伪；第三，运营成本是隐性大头，验证阶段就要把 badcase 处理、描述维护、示例更新的人工投入测出来，否则二期会因无人接手而停摆。

结论：三期的实质不是功能累加，而是风险分批释放。一期验证准确性，二期验证运营可持续性，三期验证规模化替换能力。

## 七、成功标准与验收方式

主指标只有一个：存量报表替换覆盖率，即已由本系统稳定承接、原报表可下线的数量占存量报表总数的比例。不用提问量做主指标，是因为它可以在不产生业务价值的情况下被刷高。

表 7  验收指标与分阶段目标

| 指标 | 定义 | 一期 | 二期 | 三期 |
| --- | --- | --- | --- | --- |
| 替换覆盖率（主） | 可下线存量报表数 / 存量报表总数 | 不考核 | ≥ 30% | ≥ 70% |
| 评测准确率 | 评测集中结果正确的问题占比 | ≥ 70% | ≥ 85% | ≥ 92% |
| 明说率（门槛） | 无法确定时明确说明的比例 | 100% | 100% | 100% |
| 编造率（门槛） | 错误且未声明的回答占比 | 0 | 0 | 0 |
| 取值耗时 | 提问到结果返回的中位时间 | ≤ 60 秒 | ≤ 60 秒 | ≤ 45 秒 |
| 自助占比 | 无人工介入完成取数的提问占比 | 不考核 | ≥ 70% | ≥ 80% |

质量硬门槛单独说明：“答不准就明说”是不可协商的上线条件，判定标准是编造率为 0——任何一次在证据不足时仍给出具体数字的回答，都计入编造。未达标不予上线，不设“先上线再优化”的例外。这条门槛的意义不在技术，而在信任：内部系统的用户流失不可逆。

结论：三个层次的指标各有分工——替换覆盖率回答“值不值得做”，质量门槛回答“能不能上线”，效率指标回答“用起来是否比原来快”。

## 八、主要风险与应对

下表七条风险按发生概率与影响排序，每条都给出触发信号，没有触发信号的应对措施等于没有措施。

表 8  主要风险与应对

| 风险 | 风险描述 | 触发信号 | 应对措施 |
| --- | --- | --- | --- |
| 大模型答不准 | 复杂问题生成错误 SQL，结果看似合理 | 准确率下滑、badcase 集中出现 | 控制召回质量、扩充示例、限制问题域、不确定时明说 |
| 口径不一致 | 退货率等指标的分母定义因人而异 | 同一问题不同时间结果不同 | 示例库固化口径、回答附 SQL 与口径说明 |
| 越权取数 | 改问法绕过区域与角色限制 | 审计出现跨区域查询 | 访问层强制注入权限、SQL 重写校验、越权用例拦截 |
| 外发合规 | 明细数据或个人信息被带出内网 | 出网报文含业务明细 | 只外发 schema、注释与问题，出网前做字段白名单校验 |
| 运营无人接手 | 描述不维护、示例不更新，效果持续衰减 | badcase 积压、明说率上升 | 由数据组定编兼任运营，设处理时限并纳入季度考核 |
| 用户不信任弃用 | 遇到几次错误回答后回到旧工具 | 周活下降、提问集中在少数人 | 明说机制、结果附可复核 SQL、试点期专人陪跑 |
| 范围失控 | 二期功能提前进入一期 | 需求清单持续膨胀 | 范围清单冻结，超范围需求一律进二期池 |

七条风险中，最需要管理层关注的是运营无人接手与用户信任流失两项。技术风险可以靠工程手段收敛，这两项属于组织问题——不会在验证阶段暴露，会在试点三个月后集中爆发，一旦爆发很难挽回。

结论：风险应对的关键不是列清单，而是给每条风险指定触发信号与责任人，并在试点期按月复盘一次信号是否出现。

## 九、结论

这个项目该做。现有 BI 的能力不缺，缺的是把取数入口从“配置报表”换成“提问”的那一层，这层改动带来的边际收益，明显高于继续在旧工具上堆报表。

节奏上必须先 PoC、后试点、再替代：一期只做单轮问答闭环，用一百道业务真题把准确性测出来，把“答不准就明说”作为不予上线的硬门槛。

需要清醒的是，成败不取决于模型选型，而取决于运营是否有人长期接手——表与字段描述、few-shot 示例、badcase 归因这三件事一旦断档，系统会在半年内退化成一个更贵的老工具。

因此建议：一期以数据组为运营主体立项，同步冻结范围清单与评测集；二期再谈完整权限体系与前端迁移，三期的替换覆盖率目标在此之前不对外承诺。
