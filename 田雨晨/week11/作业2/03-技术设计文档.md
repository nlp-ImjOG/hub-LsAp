# 电商数据智能问答系统（ChatBI）技术设计文档

> 版本 V1.0

## 一、技术选型与理由

选型原则是：一期跑得通、二期扩得开、全程不新增基础设施。语义层与指标中心已明确否决，准确性改由检索、示例与校验三条工程手段承担，因此选型只围绕这三点展开。

表1-1 技术选型与备选方案

| 选型项 | 采用 | 理由 | 被否决方案及原因 |
| --- | --- | --- | --- |
| Web 框架 | FastAPI | 原生异步、Pydantic 校验、自动 OpenAPI | Flask 缺异步与校验；Django 偏重，ORM 与 Admin 用不上 |
| Agent 编排 | OpenAI Agents SDK | 轻量、工具调用原生、编排即代码 | LangChain 抽象层厚、调用链难排查、版本变动频繁 |
| 工具层 | FastMCP | 取数与编排解耦，可独立鉴权、限流、复用 | 内部函数绑死进程，无法单独限流与替换 |
| 一期前端 | Streamlit | 纯 Python，两天出可交互原型 | 直接上 Vue3 需前后端联调，验证期成本过高 |
| 存储 | 直读 MySQL | 数据几十万级、T+1，无需同步链路 | 不引入数仓与 ES，避免第二份数据与口径分叉 |
| 大模型 | 公网 API | 效果与成本优于自建，无 GPU 运维 | 私有化部署投入大、迭代慢；外发边界见第九章 |

结论：六项选型共用一个标准——不新增需要专人运维的组件；凡引入第二份数据或第二套口径的方案一律否决。

## 二、总体架构

系统分六层，调用方向自上而下单向，禁止跨层回跳。取数能力收敛到 MCP 工具层这一条通道，它是架构中唯一能接触生产数据的位置。

表2-1 分层职责边界

| 层次 | 职责 | 明确不做 |
| --- | --- | --- |
| 前端（Streamlit / Vue3） | 提问、结果表、SQL 展示、看板 | 不做权限判定与数据加工 |
| 应用层（FastAPI） | 认证、会话、审计、看板、元数据维护 | 不生成 SQL、不直接调模型 |
| 编排层（Agents SDK） | 意图理解、工具选择、重试决策 | 不直连数据库 |
| 工具层（FastMCP） | 工具暴露、参数校验、限流与超时 | 不承载业务口径解释 |
| 数据访问层 | 只读连接、AST 校验、权限改写、脱敏 | 不做结果解读 |
| MySQL | 业务库只读、系统库读写 | 不接受任何 DDL / DML |

工具层独立成 MCP 的理由有三：它独占数据库只读账号，独立进程才能单独限流与熔断；同一套工具可被二期 Vue3 前端与运维脚本复用；协议标准化后，更换编排框架不影响取数实现。

结论：分层的收益不在代码整洁，而在把"能碰到数据的那一段"压到可审计的最小面积。

## 三、Agent 设计

Agent 只承担一个职责：把自然语言问题翻译成一次能通过校验的 SQL；做不到时明确拒答。它不解释业务口径，不猜测字段含义，遇歧义宁可反问。

表3-1 Agent 工具集与签名

| 工具 | 签名 | 用途 |
| --- | --- | --- |
| search_relevant_tables | (query: str, top_k: int = 3) | 向量召回相关表 |
| get_table_schema | (tables: list[str]) | 返回字段名、类型与注释 |
| list_tables | (domain: str \| None) | 列出主题内表清单 |
| validate_sql | (sql: str, user_ctx: dict) | 语法、字段与权限预检 |
| execute_query | (sql: str, limit: int = 1000) | 执行并返回结果集 |
| get_few_shots | (question: str, k: int = 2) | 取相似示例 |

一次问答走七步：意图理解、表召回、schema 注入、SQL 生成、校验、执行、结果组织。执行报错时把错误文本回灌，重写后重跑全链路校验，重试上限 2 次。

终止条件有三：SQL 通过校验且执行成功；重试次数达上限；命中拒答规则。三者任一满足即结束，不再追加调用。

结论：把重试钉死在 2 次，是用确定成本换可预期延迟——重试越多，单次响应越不可控，体验反而更差。

## 四、准确性保障机制

四条机制按投入产出排序：召回决定模型看不看得见表，示例决定它写得对不对，校验决定错得可不可控，拒答决定错了会不会误导用户。

### （一）schema 检索

以表为最小切分单元，把表名、表注释、字段名与字段注释拼成一段表级文档，按四个主题分库索引；字段不单独成块，避免召回碎片化。问题向量化后取 Top3 表，最高分低于阈值则扩到 Top5 并提示置信度偏低。上限 5 张，是因为超过 5 张后上下文冗余、生成质量明显下降。

### （二）few-shot 示例

示例来自三处：评测集中的高质量问答、运营从 badcase 修正后的正确写法、被用户确认过的历史查询。按向量相似度取 2 条注入，多了反而干扰。运营后台可增删改，保存即生效，不必发版。

### （三）SQL 校验与自动纠错

校验五步串联：语法解析、字段存在性、权限条件注入、dry-run 预检、正式执行。任一步失败都把原始报错回灌模型重写，重写后重跑全链路校验，而不是只补语法。

### （四）拒答与澄清策略

三道拦截：问题命中歧义词典（如"销售额"是否含退款）则反问；召回最高分低于阈值则回复"没有找到相关数据表"；重试两次仍失败则明确回答"这个问题我答不准"。任何情况下都不返回推测值。

表4-1 分阶段准确率目标

| 阶段 | 高频问题准确率 | 拒答准确率 | 统计口径 |
| --- | --- | --- | --- |
| 一期 PoC | ≥70% | ≥90% | 单表、双表查询 |
| 二期试点 | ≥85% | ≥90% | 含多轮与图表 |
| 三期替代 BI | ≥92% | ≥95% | 按存量报表维度 |

明说率 100% 与编造率 0 为全程硬门槛，一期起即考核，不随阶段放宽。

结论：准确率不达标时先补召回与示例，最后才动模型；拒答准确率是上线硬门槛，宁可少答不可错答。

## 五、MCP 工具层设计

表5-1 工具清单

| 工具名 | 入参 | 出参 | 异常 | 权限要求 |
| --- | --- | --- | --- | --- |
| list_tables | domain | 表名与注释列表 | 无 | 登录即可 |
| search_relevant_tables | query，top_k | 表名与相似度 | 检索不可用 | 登录即可 |
| get_table_schema | tables[] | 字段名、类型、注释 | 表不存在 | 按可见范围过滤 |
| validate_sql | sql，user_ctx | 是否通过与错误原因 | 解析失败 | 登录即可 |
| execute_query | sql，limit | 列名与行数据 | 超时、超行、语法错 | 按行级权限 |
| get_few_shots | question，k | 示例问答对 | 无 | 登录即可 |
| get_user_scope | user_id | 可查区域编码 | 用户不存在 | 管理员 |

表5-2 工具层安全约束

| 约束项 | 取值 | 说明 |
| --- | --- | --- |
| 数据库账号 | 只读账号 | 仅有 SELECT 权限 |
| 单次超时 | 30 秒 | 超时即杀连接 |
| 最大返回行数 | 5000 行 | 超出截断并标注 |
| 禁止语句 | DDL、DML、多语句、select * | 解析后统一拦截 |
| 调用频率 | 单用户 20 次/分钟 | 超出返回限流提示 |

工具描述本身就是 prompt。模型决定调不调、怎么填参，完全依赖 description 与参数说明，因此描述必须写清适用场景、必填约束与典型错误。这部分由运营在后台维护，不进代码仓库，改描述不必发版。

结论：工具层的真实产出不是接口，而是一份人和模型都能读懂的说明书。

## 六、数据访问与安全设计

行级权限的落地方式有二：字符串拼接 WHERE，或解析语法树后注入条件。选择 AST 方案（以 sqlglot 解析，在 WHERE 节点追加区域条件），因为字符串拼接在子查询、UNION、注释符场景下极易被绕过，而 AST 能保证条件落在每一层查询上。

手机号默认将中间四位打码，在返回前对结果集做字段级处理；仅有敏感字段权限的角色（管理员）才看到明文，且每次查看单独记一条审计。

表6-1 关键安全参数

| 项目 | 取值 | 落地位置 |
| --- | --- | --- |
| 只读账号 | bi_reader | 数据访问层 |
| 危险语句拦截 | 非 SELECT 一律拒绝 | AST 校验 |
| 结果行数上限 | 5000 行 | 工具层 |
| 执行超时 | 30 秒 | 连接与语句级 |
| 脱敏规则 | 手机号第 4 至 7 位打码 | 结果集处理 |
| 审计留存 | 全量，保存 12 个月 | 系统库 |

审计日志字段固定为：操作人、角色、区域范围、原始问题、生成 SQL、改写后 SQL、执行耗时、返回行数、是否脱敏、是否拒答、错误码。用户可见的每一次查询都必须留下一条记录。

结论：安全不能依赖模型自觉，只能依赖模型之后的那道解析与改写。

## 七、数据模型设计

系统库与业务库物理分离：业务库只读、不做任何写入；系统库保存账号、会话、审计与运营资产，共 12 张核心表。

表7-1 系统库核心表

| 表名 | 用途 | 关键字段 |
| --- | --- | --- |
| sys_user | 用户与角色 | user_id BIGINT 主键；username VARCHAR 登录名；role_code VARCHAR 取 admin/manager/staff；region_scope VARCHAR 可查区域；status TINYINT |
| chat_session | 会话 | session_id BIGINT 主键；user_id BIGINT；title VARCHAR；created_at DATETIME |
| chat_message | 消息 | msg_id BIGINT 主键；session_id BIGINT；role VARCHAR 取 user/assistant；content TEXT；sql_text TEXT |
| query_log | 查询记录与 SQL 明细 | query_id BIGINT 主键；msg_id BIGINT；raw_sql TEXT；rewritten_sql TEXT；row_count INT；elapsed_ms INT；status VARCHAR |
| dashboard | 看板与图表 | board_id BIGINT 主键；user_id BIGINT；name VARCHAR；chart_json JSON 图表配置；shared TINYINT |
| meta_table | 表元数据 | table_id BIGINT 主键；table_name VARCHAR；table_comment VARCHAR；domain VARCHAR；enabled TINYINT |
| meta_column | 字段元数据 | col_id BIGINT 主键；table_id BIGINT；column_name VARCHAR；data_type VARCHAR；column_comment VARCHAR；sensitive TINYINT |
| prompt_asset | 同义词与 few-shot 示例 | asset_id BIGINT 主键；asset_type VARCHAR 取 synonym/few_shot；content TEXT；embedding_id VARCHAR；enabled TINYINT |
| badcase | 错例 | case_id BIGINT 主键；query_id BIGINT；reason VARCHAR；fixed_sql TEXT；status VARCHAR；owner VARCHAR |
| eval_case | 评测集与评测结果 | eval_id BIGINT 主键；question VARCHAR；expect_sql TEXT；tags VARCHAR；last_result VARCHAR；last_run_at DATETIME |
| audit_log | 审计日志 | log_id BIGINT 主键；user_id BIGINT；action VARCHAR；detail TEXT；ip VARCHAR；created_at DATETIME |
| model_config | 模型配置 | cfg_id BIGINT 主键；provider VARCHAR；model_name VARCHAR；temperature DECIMAL；max_retry INT；enabled TINYINT |

与业务库的关系只有一条：只读。系统库通过 meta_table 与 meta_column 描述业务库结构，二者不做外键、不做同步写入，业务库的任何变更都不会由本系统发起。

结论：角色不单独建表，因为角色只有三类、权限矩阵固定，用编码字段可省一次关联查询。

## 九、部署与工程结构

部署五个进程：Streamlit 前端、FastAPI 应用、FastMCP Server、MySQL、向量检索。向量检索一期用落盘的本地索引（FAISS 文件），因为表只有几十张、字段几百个，不值得再养一个向量数据库；二期表量上来再评估。

表9-1 配置与环境变量清单

| 变量 | 示例 | 说明 |
| --- | --- | --- |
| DB_READONLY_URL | mysql://bi_reader@10.0.0.12/bi | 业务库只读连接 |
| SYS_DB_URL | mysql://bi_app@10.0.0.12/chatbi | 系统库连接 |
| LLM_PROVIDER | openai-compatible | 公网模型协议 |
| LLM_MODEL | gpt-4o-mini | 默认模型 |
| LLM_TIMEOUT | 60 | 单次调用超时秒数 |
| MCP_ENDPOINT | http://127.0.0.1:8100 | 工具层地址 |
| MAX_RETRY | 2 | SQL 重试上限 |
| ROW_LIMIT | 5000 | 返回行数上限 |
| VECTOR_STORE | local:./data/index | 向量索引位置 |

外发边界：出去只有 schema、字段注释与用户问题；明细数据、结果集与审计日志一律不出内网，出网代理只放行模型接口域名。

后端目录结构如下，模块按职责切分，routers 只做参数与鉴权，业务全部落在 services。

```
app/
  routers/       REST 路由，鉴权与参数校验
  services/      问答、看板、元数据、审计的业务逻辑
  agent/         Agents SDK 编排与提示词模板
  mcp_server/    FastMCP 工具实现与安全约束
  models/        系统库表模型与 Pydantic 出入参
  core/          配置、只读连接、AST 权限改写
```

结论：一期不引入独立向量库与消息队列，把进程数压到五个以内，是为了让兼职运维的 BI 团队接得住。

## 十、评测与运维

评测集从存量报表反推：一张常用报表对应 5 至 10 个典型问法，一期先建 100 条，覆盖四个主题与高频口径。每条记录问题、预期 SQL 与判定方式（结果比对或 SQL 比对）。

准确率等于结果与预期一致的问题数除以参评问题数；多轮与图表类问题单列，不计入主指标。模型或 prompt 变更前必须跑全量回归，通过率低于上一版即回滚。

badcase 有两个入口：用户在结果页点"不准"，以及审计抽查中发现。每条 badcase 必须落到一个动作——补示例、补字段注释、改工具描述或判定为暂不支持；处理完即进评测集，形成闭环。

表10-1 监控指标与告警阈值

| 指标 | 统计口径 | 告警阈值 |
| --- | --- | --- |
| 端到端 P95 延迟 | 单次问答耗时 | ≥15 秒 |
| SQL 重试率 | 重试次数除以查询数 | ≥30% |
| 拒答率 | 拒答数除以查询数 | ≥25% |
| 执行失败率 | 异常数除以查询数 | ≥10% |
| badcase 周增量 | 每周新增条数 | ≥20 条 |

结论：重试率与拒答率同时上升，说明召回或元数据出了问题而非模型变笨，排查顺序应从元数据开始。

## 十一、关键技术风险与预案

表11-1 主要风险与预案

| 风险 | 表现 | 预案 |
| --- | --- | --- |
| 大模型生成 SQL 不稳定 | 同问不同 SQL、口径漂移 | 固定 temperature 为 0；示例固定；评测集作为回归卡口 |
| 表结构变更导致召回失效 | 召回不到表、字段不存在 | 元数据每日巡检比对，变更即重建索引并告警 |
| 公网模型延迟与限流 | 超时、返回 429 | 超时 60 秒降级重试；队列削峰；预留备用模型路由 |
| 权限改写遗漏导致越权 | 看到他人区域数据 | AST 全链路注入；越权用例集上线前逐条验证；审计抽查 |
| 运营维护成本过高 | 元数据与示例长期无人更新 | 维护动作嵌入 badcase 流程；每月一次资产盘点 |

五条风险里有两条必须在上线前证伪：权限改写遗漏与模型编造结果。前者用越权用例集在测试环境逐条验证，后者用拒答率与人工抽查共同约束，任一不达标不予上线。

结论：风险预案的价值不在事后补救，而在事前把它变成一条可执行的验收用例。
