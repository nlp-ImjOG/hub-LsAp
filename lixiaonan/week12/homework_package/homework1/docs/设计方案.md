# 楼道消防隐患识别系统 — 设计方案

> 作业1：参考《案例-多模态内容理解.ipynb》，构建带前后端的多模态应用，网页打开进行拍照，调用 GLM-4.1V-Flash / Qwen-VL 进行楼道风险识别。
>
> 文档日期：2026-10-28

---

## 1. 需求与目标

| 项 | 说明 |
|---|---|
| 输入 | 手机/PC 浏览器：① 调用摄像头拍照 ② 上传本地图片 |
| 处理 | 后端调用多模态大模型（GLM-4.1V-Flash / Qwen-VL）分析图片 |
| 输出 | 五级分类：**高风险 / 中风险 / 低风险 / 无风险 / 非楼道** + 判断依据 |
| 特点 | 单张图片实时识别（秒级返回），无需训练模型 |

**分级标准（来自作业要求）**

- **高风险**：楼道中出现电动车、电瓶、飞线充电等可能起火的元素
- **中风险**：楼道中存在大量堆积物严重影响通行，或堆放大量纸箱、木质家具等能造成火势蔓延的堵塞物
- **低风险**：存在楼道堆物现象但不严重
- **无风险**：楼道干净，无堆放物品
- **非楼道**：与楼道无关的图片

**技术路线依据**（案例 notebook cell 18 的结论）：大模型方案 2 小时即可写完并部署（成本 24G GPU / API 调用，速度约 1 秒）；YOLO 需标注、训练、调参 5 天。故选用多模态大模型而非传统视觉模型，零训练、Prompt 即可调优，最快交付。

## 2. 总体架构

```
┌─────────────────┐  HTTPS POST   ┌──────────────────┐  OpenAI兼容API   ┌────────────────────┐
│  浏览器（手机优先） │ ───────────▶ │   FastAPI 后端     │ ───────────────▶ │ 多模态大模型（可切换） │
│  · getUserMedia   │  base64图片   │  · 图片校验/压缩    │  图片 + Prompt   │ · GLM-4.1V-Flash    │
│  · 拍照/上传       │              │  · Prompt 组装     │ ◀─────────────── │ · qwen-vl-plus      │
│  · 结果着色展示    │ ◀─────────── │  · JSON解析容错    │   结构化JSON     │ · 本地Qwen2.5-VL(可选)│
└─────────────────┘   JSON结果    └──────────────────┘                  └────────────────────┘
```

**分层职责**

- **前端**：只负责取图（拍照/上传）、压缩、展示，**不接触 API Key**
- **后端**：图片校验、Prompt 管理、模型调用、JSON 容错解析、历史记录
- **模型层**：适配器模式封装，一行配置切换模型（OpenAI 兼容协议的云端 API / 本地 transformers，两种实现）

> **关于"ds flash 4.1"**：DeepSeek 官方 API 目前无视觉模型，推测指智谱 **GLM-4.1V-Flash**（免费）或课程指定网关。方案中模型名做成配置项，同一套代码可切 GLM-4.1V-Flash / qwen-vl-plus / 本地 Qwen2.5-VL，兼容两种要求。

## 3. 接口设计

### 3.1 图片识别 `POST /api/analyze`

```jsonc
// 请求
{ "image": "data:image/jpeg;base64,..." }

// 响应
{
  "risk_level": "high",            // high | medium | low | none | not_corridor
  "risk_label": "高风险",
  "confidence": 0.92,
  "elements": ["电动车", "飞线充电"],
  "reason": "楼道内停放电动车且从窗口飞线充电",
  "suggestion": "立即移出电动车，拆除飞线",
  "model": "glm-4.1v-flash",
  "elapsed_ms": 1350
}
```

### 3.2 辅助接口

- `GET /api/health`：服务与模型连通性自检
- `GET /api/history`：最近识别记录（可选，M4 实现）

## 4. 核心 Prompt（在案例 cell 17 基础上强化）

关键改动：角色化 + 强制 JSON 输出 + 明确边界定义。

```
你是专业的消防安全检查员，负责检查居民楼楼道。请分析照片并判定隐患等级。

【判定标准（从严到宽，取最高命中等级）】
- high    高风险：出现电动车、电瓶、飞线充电、明火等可能起火的元素
- medium  中风险：大量堆积物严重影响通行，或大量纸箱、木质家具等易燃堵塞物
- low     低风险：存在堆物现象但不严重、数量少、不挡通道
- none    无风险：楼道干净整洁，无堆放物品
- not_corridor 非楼道：与楼道无关的照片（室外、客厅、人物等）

【输出要求】只输出一个 JSON 对象，禁止任何其他文字或 markdown：
{"risk_level": "...", "confidence": 0~1, "elements": ["关键元素"], "reason": "50字内判断依据", "suggestion": "50字内处置建议"}
```

**解析容错链**：`temperature=0.1` → 正则提取 `{...}` → 解析失败带错误信息重试 1 次 → 仍失败返回 503 及模型原始文本。

## 5. 前端交互流程

```
打开页面 → [拍照] / [上传] 两个Tab
  ├─ 拍照：getUserMedia({video:{facingMode:'environment'}}) → video 预览 → 点快门 → canvas 截图
  └─ 上传：<input type="file" accept="image/*" capture="environment">（同时兜底手机系统相机）
→ 预览确认 → canvas 压缩至长边 1024px / JPEG 0.8（省 token、提速）→ POST /api/analyze
→ Loading 动画 → 结果卡片（按等级着色 + 图标）
```

**结果展示配色**

| 等级 | 颜色 |
|---|---|
| 高风险 | 🔴 红 |
| 中风险 | 🟠 橙 |
| 低风险 | 🟡 黄 |
| 无风险 | 🟢 绿 |
| 非楼道 | ⚪ 灰 |

卡片内容：`risk_label` 大字 + `elements` 标签 + `reason` / `suggestion` + 耗时；页面下方保留本次会话的历史记录列表。

**关键技术坑（提前规避）**

1. `getUserMedia` 要求**安全上下文**（`localhost` 或 HTTPS），局域网 IP + HTTP 下手机浏览器会拒绝
   → 电脑端用 localhost 调试；真机演示用 ngrok/Caddy 起 HTTPS；或直接走 `capture="environment"` 的文件上传通道（调系统相机，无此限制）
2. 后端再兜底压缩一次（Pillow，>5MB 拒收），防超大图
3. API Key 只存后端 `.env`，前端零密钥

## 7. 开发计划与验证

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 后端 MVP | FastAPI + 模型适配器 + Prompt，curl 压测 | `test_images/` 五类全部分类正确 |
| M2 前端上传 | 上传 → 识别 → 结果卡片 | PC 浏览器全流程跑通 |
| M3 摄像头 | getUserMedia 拍照 + 手机 HTTPS 真机 | 手机拍照→出结果 ≤ 3s |
| M4 收尾 | 历史记录、异常提示、边界样本回归 | 边界 case 通过，README 部署说明 |

**风险预案**

| 风险 | 应对 |
|---|---|
| 模型输出不稳定 | JSON 约束 + 解析容错重试 |
| 免费接口限流 | 后端队列串行 + 前端防重复提交 |
| 无 API Key 环境 | 本地 Qwen2.5-VL 兜底（案例已验证：24G GPU、约 1s/张） |
| API Key 泄露 | 仅存后端 `.env`，前端不接触 |
