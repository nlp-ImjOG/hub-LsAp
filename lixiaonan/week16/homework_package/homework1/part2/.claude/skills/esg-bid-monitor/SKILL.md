# ESG 投标信息汇总与每日监控

本技能把"ESG/双碳招投标信息工作"拆成两条共享同一条数据管线的产出线：

- **report 回溯汇总模式**（默认）：检索过去一段时间的 ESG/可持续发展/双碳相关招标与中标公告，抽取为结构化记录入库，统计热点与金额分布，产出《ESG/双碳招投标市场回顾报告》。
- **monitor 每日监控模式**：增量检索近 24h（或自上次运行以来）新发布的 ESG 相关招标公告，去重后产出《ESG 标讯速递》并推送。

所有数据落在**当前工作目录**的 `data/` 下：`bids.jsonl` 标讯库、`notes/` 检索笔记、`reports/` 回溯报告、`daily/` 每日速递、`state.json` 运行状态。两条管线共用同一份标讯库——今天入库的招标公告，就是未来回溯分析的原始素材。

## Phase 0 输入解析与初始化

1. **判定模式**：
   - 提到"监控/跟踪/推送/今日新增/标讯速递/商机" → **monitor**
   - 提到"分析/汇总/回顾/过去X年/金额分布/热点" → **report**
   - 均未提及 → 默认 **report**，并在开场告知用户当前模式，如需另一模式请说明
2. **确定参数**（用户未指定时用默认值，并在产出中声明）：
   - report：时间范围 = 近 2 年（以今天为基准回推）；主题 = ESG 全主题；地区 = 全国
   - monitor：监测窗口 = 「近 24h」与「自 `state.json` 的 `last_run` 以来」的**并集**（窗口起点取两者中更早的 min）——刚跑过也至少回看 24h，漏跑多天则回补到上次运行，两种情况都不丢条目
3. **初始化工作区**：确认/创建 `data/{notes,reports,daily}` 目录；读取 `data/state.json`（不存在则视为首次运行）；读取 `data/bids.jsonl` 已有的 record_id 集合，作为本次去重基线
4. 以今天的日期为锚点，明确本次统计期的起止日期，写入检索笔记开头

为什么先读状态：bids.jsonl 与 state.json 是跨运行累积的资产，不读会造成重复入库或漏检。

## Phase 1 自主检索采集

先读 `references/search-playbook.md`（数据源与扇出策略）和 `references/keywords.md`（主题词库），再开始检索。

- **report 模式**：按 playbook 的检索词矩阵扇出——主题×阶段共 10 条主线，每线 4~6 组检索词，同一批独立检索**并行发起**（并行是为了绕开单次搜索结果数量上限，也省总时长）。同一主题轮换四种角度：泛搜、site 限定、地区限定、年度限定。
- **monitor 模式**：按 playbook 的监控策略执行一轮"主题词 × 招标/采购 × 近24h/今日"的并行检索，重点保时效而非穷尽。
- 对关键命中（疑似含完整金额/中标人的公告页）用 WebFetch 抓原文补充细节——搜索摘要往往缺金额，原文才有。
- 每完成一批检索，把"关键词批次、命中数、代表链接"追加落盘 `data/notes/search_<日期>_<模式>.md`。长会话中上下文可能被压缩，笔记是防丢失的唯一保险。

**数量下限**：report 模式每条主线有效候选 ≥8 条为达标；不足则换词/换 site 补检一轮（最多一轮）。仍不足的主线如实记录"公开可检索样本不足"——宁缺毋假，不要为凑数放宽相关性标准。

## Phase 2 抽取与筛选

先读 `references/extraction-rules.md`（字段模型、金额规范化、去重指纹的精确定义），然后逐条处理候选公告：

1. **相关性判定**（双条件）：标题或正文核心命中主题词，且标的与 ESG/双碳目的相关。仅字面巧合（如"绿色"实为普通绿化带施工）判为不相关，直接丢弃。
2. **字段抽取**：按 18 字段模型抽取，优先级 = 公告正文 > 搜索摘要 > 标题；无法确认的字段置 null，绝不猜测——错误数据比缺失数据危害大。
3. **金额规范化**：按换算表统一为万元；区分"预算金额/最高限价/成交金额"三种口径，成交价优先。
4. **去重入库**：按指纹规则计算 record_id，与基线比对——新项目追加写入 `data/bids.jsonl`；已存在且 stage 升级（招标→中标）则更新原记录的 stage/winner/amount_wan。每条记录必须带 url 与 publish_date，缺任一则不入库。

**边采边入库**：每批检索确认的条目立即写入 bids.jsonl，不要攒到最后一次性写——长会话中断时已入库的数据不丢。入库后复核一行数：本次新增 N 条、更新 M 条、跳过重复 K 条，写进笔记。

## Phase 3 统计分析与成报

### report 模式

1. 先读 `references/analysis-guide.md`（统计口径）与 `references/report-template.md`（报告模板）。
2. 运行统计脚本获得权威数字（不要心算统计，报告数字必须与脚本输出一致）：
   ```bash
   python .claude/skills/esg-bid-monitor/scripts/stats.py data/bids.jsonl --start-date <起> --end-date <止>
   ```
3. 按模板撰写《ESG/双碳招投标市场回顾报告》，落盘 `data/reports/ESG招投标市场回顾_<起>_<止>.md`：
   - 样本说明段必须写清：总样本量、来源构成、金额可解析率、局限性声明
   - 主题分布、金额分桶、省份 Top10、月度趋势用 Mermaid 图呈现（规范见 analysis-guide）
   - 第六章"趋势研判与投标建议"是本报告的价值所在：把统计结论翻译成投标企业可执行的建议
4. 逐项过一遍 report-template.md 末尾的质量自查清单，不合格先修复再交付。

### monitor 模式

1. 读 `references/report-template.md` 中的每日速递模板。
2. 筛选本次窗口内新入库、stage 为招标/采购类公告、且不在已推送范围（state.json 的 daily_log）中的条目。
3. 排序规则：重点推荐 = 高金额（≥500 万）或大客户（中央/省级预算单位）或 3 日内截止；其余进一览表。
4. 落盘 `data/daily/ESG标讯速递_<今天>.md`（同日重跑覆盖），并向用户报告文件路径与 3~5 条重点摘要——这就是"推送"动作的默认形态。
5. 更新 `data/state.json`：last_run = 本次时间，daily_log 追加本次日期。

## 状态管理规则

- 每次运行结束（无论哪条管线）都更新 state.json 的 last_run；seen_count 与 bids.jsonl 行数保持一致
- state.json 结构：`{"last_run": "...", "seen_count": N, "daily_log": ["YYYY-MM-DD", ...], "webhook": null}`
- 用户配置了 webhook（飞书/钉钉/企微机器人地址）时，monitor 模式在落盘后把速递转纯文本 POST 到该地址；POST 失败不影响落盘

## 失败兜底

- 某主题检索无结果：换词/换 site 补检一轮；仍无结果则如实标注"公开可检索样本不足"，宁缺毋假
- WebFetch 抓原文失败：允许以搜索摘要入库，但 summary 末尾标注"（据搜索摘要，原文未核验）"
- 同一 URL 反复抓取失败：最多重试 1 次，然后放弃并记录到笔记
- 网络整体异常：报告已完成的进度与笔记位置，建议稍后重跑——状态已落盘，重跑不会重复劳动
