# ESG 投标信息汇总 SKILL/AGENT 实施文档

> **作业来源**：第 16 周《Agent 应用部署：Skills 与 OpenClaw》homework1 / part2 · 案例二
> **编制日期**：2026-11-24
> **交付目标**：构建一个「ESG 投标信息汇总」Skill，实现**自主搜索互联网 → 自主筛选信息 → 结构化沉淀 → 统计分析成报**的完整闭环，同时支撑两个场景：①过去 2 年 ESG/可持续发展/双碳中标情况回溯分析；②每日新增 ESG 相关招标信息监控推送。

---

## 一、项目概述

### 1.1 要解决的问题

ESG/双碳是当前政府采购与企业招标的高热赛道。投标决策者需要两类截然不同但底层数据同源的能力：

1. **回溯分析**：了解过去 2 年市场上"谁在买 ESG 服务、买什么、花多少钱、谁中标了"，用于研判热点方向、制定投标策略、参考报价区间；
2. **日常监控**：每天自动捕获新发布的 ESG 相关招标公告，第一时间推送商机，避免人工每天翻各大招标平台。

传统做法依赖付费标讯平台会员 + 人工每日盯盘，本作业要求将其沉淀为一个可复用的 **Claude Code Skill**，由 Agent 自主完成检索、筛选、结构化、分析与推送。

### 1.2 核心挑战

| 挑战 | 说明 | 应对思路 |
|---|---|---|
| 数据源分散且有登录墙 | 中国政府采购网、全国公共资源交易平台、各省交易中心、千里马/采招网/剑鱼等聚合平台星罗棋布，聚合平台普遍收费 | 以"通用搜索引擎 + 官方平台直采"为主的多源冗余策略，聚合平台仅作线索 |
| "过去 2 年"体量巨大 | 两年内双碳/ESG 相关公告数以十万计，无法穷尽 | 明确统计口径为"公开可检索样本"，分主题×分阶段×分批次扇出检索，报告中如实声明样本边界 |
| 信息非结构化 | 公告正文格式五花八门，金额表述有"万元/亿元/元/免费获取"多种写法 | 内置字段抽取规则 + 金额规范化规则（见 4.5），统一落盘为 JSONL |
| 一标多公告 | 同一项目会先后出现招标公告、更正公告、中标公告 | 增加 stage（阶段）字段，按"项目名+采购人"归一去重，保留全阶段演化 |
| 金额缺失率高 | 大量公告不披露预算/成交金额 | 缺失字段置 null 并标注"金额未披露"，统计时单列缺失率，不冒充完整数据 |
| 每日推送的时效与去重 | 需要知道"哪些是新的" | 增量检索（近 24h）+ 本地 seen 指纹库去重 + state.json 记录上次运行时间 |

### 1.3 运行环境与能力支撑

- 运行环境：Claude Code 会话，原生具备 `WebSearch`（联网检索）、`WebFetch`（抓取原文）、`Bash`（跑统计脚本）、`Write`/`Read`（落盘与回读），**无需任何外部 API Key 或第三方依赖**；
- 回溯期定义：以调用日为基准回溯 2 年。本次设计基准日为 **2026-11-24**，即统计期约 **2024-11 ~ 2026-11**；
- 定时能力：日常部署采用系统 crontab + Claude Code 无头模式（`claude -p`）；会话内演示可采用 `CronCreate` 定时任务（见第六章）。

## 二、需求分析

### 2.1 原始需求

> 案例二：ESG 投标信息汇总 SKILL/AGENT
> 1. 汇总过去 2 年 ESG、可持续发展、双碳相关的中标情况，分析汇总热点招标情况及中标金额分布。
> 2. 监控新的跟 ESG 相关的招标情况，每天推送新的招标信息。
>
> 构建这个 skill，完成上述案例。skill 需要自主搜索互联网的内容，自主筛选信息，形成报告。希望最终报告得到的效果越好越好。

### 2.2 需求拆解

**（1）功能维度 —— 两个场景映射为 Skill 的两个模式：**

| 需求条目 | 关键动作 | 对应 Skill 模式 | 核心产出 |
|---|---|---|---|
| ① 汇总过去 2 年 ESG/可持续发展/双碳**中标**情况 | 回溯检索 → 抽取中标记录（中标人、金额）→ 热点分析 → 金额分布 | **回溯汇总模式**（report） | 两年市场回顾报告（md + html），含主题热点、地域、趋势、金额分布、中标格局 |
| ② 监控新 ESG 相关**招标**，每天推送 | 增量检索近 24h 招标公告 → 去重 → 相关性筛选 → 生成速递 → 推送 | **每日监控模式**（monitor） | 每日 ESG 标讯速递（md），含新招标列表、重点推荐、截止提醒 |

注意需求①关注**中标结果**（成交侧），需求②关注**新招标**（商机侧）——底层数据模型统一，但阶段字段与推送口径不同。

**（2）分析维度 —— "热点招标情况 + 中标金额分布"具体化为 6 个统计视角：**

| 统计视角 | 回答的问题 |
|---|---|
| ESG 主题分布 | 双碳、绿色环保、清洁能源、可持续咨询、绿色金融哪个最热？ |
| 项目类型分布 | 买的是咨询服务、信息化系统、工程还是设备？ |
| 地域分布 | 哪些省份需求最旺？ |
| 采购人画像 | 政府机关、国企、高校、上市公司谁在出手？ |
| 月度发布趋势 | 两年内热度是上升还是波动？ |
| 中标金额分布 | 金额区间如何分布？总额/均值/中位数？大单被谁拿走？ |

**（3）能力维度 —— 三个"自主"意味着：**

- **自主搜索**：数据源清单、检索词矩阵、分批扇出策略内置在 Skill 中；
- **自主筛选**：ESG 相关性判定规则、时间窗过滤、来源分级、去重规则显式写入 Skill；
- **自主成报**：结构化存储、统计口径、报告模板、质量自查清单以文件固化，保证产出稳定可复现。

## 三、总体设计

### 3.1 设计原则

1. **一库两用**：招标与中标是同一条数据生命周期的两个阶段，统一用一份 JSONL 标讯库承载，回溯分析与每日监控共用同一套检索/抽取/去重管线，仅输出端不同；
2. **通用化优先**：时间范围、主题词、地区均可参数化，"过去 2 年 / ESG 全主题"只是默认值，遵循 skill-creator 规范避免为眼前用例过拟合；
3. **口径诚实**：公开互联网无法穷尽全部历史公告，统计结论必须明确声明"基于公开可检索样本"，金额缺失率、来源构成全部如实披露，绝不冒充全量；
4. **渐进式加载**：SKILL.md 只放工作流主干（<500 行），检索词矩阵、关键词库、抽取规则、统计口径、报告模板下沉到 `references/` 按需加载；
5. **零外部依赖**：检索用原生 `WebSearch`/`WebFetch`；统计脚本仅用 Python 标准库；图表优先 Markdown 内嵌 Mermaid，HTML 版为可选增强。

### 3.2 技术架构与工作流（双模式共享管线）

```
用户输入（模式?，时间范围?，主题/地区?）
        │
        ▼
┌─ Phase 0 输入解析与初始化 ──────────────────────────────────┐
│ 模式判定：回溯汇总(report，默认) / 每日监控(monitor)            │
│ report：时间范围=近2年(2024-11~2026-11)；monitor：窗口=近24h   │
│ 读取 data/state.json（seen 指纹数、last_run）；建目录           │
└────────────┬────────────────────────────────────────────────┘
             ▼
┌─ Phase 1 自主检索采集（读 references/search-playbook.md）────┐
│ 检索词矩阵扇出：主题词(5类×细分词) × 阶段词(招标/中标) ×        │
│ site限定(ccgp/cebpubservice/省交易中心) × 批次，并行发起        │
│ 关键命中 → WebFetch 抓公告原文；检索笔记随时落盘 data/notes/     │
└────────────┬────────────────────────────────────────────────┘
             ▼
┌─ Phase 2 抽取与筛选（读 references/extraction-rules.md）─────┐
│ ESG 相关性判定 → 字段抽取(项目/阶段/采购人/中标人/金额/地区/日期) │
│ → 金额规范化(万元/亿元/元 → 万元数值，缺失=null)                 │
│ → 去重(指纹=归一化项目名+采购人，辅以 URL) → 追加写入 bids.jsonl │
└────────────┬────────────────────────────────────────────────┘
             ▼
┌─ Phase 3 统计分析与成报（读 analysis-guide / report-template）┐
│ report：跑 scripts/stats.py 出统计结果 → 生成两年回顾报告        │
│ （主题热点/金额分布/地域/趋势/中标格局）→ 质量自查 → 落盘          │
│ monitor：过滤 stage=招标公告 且未推送 → 排序(高金额/临截止)      │
│ → 生成当日速递 → 落盘 data/daily/ → 推送 → 更新 state.json     │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 数据模型与存储设计

**结构化标讯库 `data/bids.jsonl`（每行一条 JSON 记录）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `record_id` | string | 去重指纹：`sha1(归一化项目名+采购人)` 前 12 位 |
| `project_name` | string | 项目名称（规范化：去括号备注、全半角统一） |
| `stage` | enum | 招标公告 / 更正公告 / 中标公告 / 成交结果 / 入围公示 |
| `theme` | string[] | ESG 主题标签：双碳 / 绿色环保 / 清洁能源 / 可持续咨询 / 绿色金融（可多选） |
| `industry_type` | enum | 咨询服务 / 信息化系统 / 工程建设 / 设备采购 / 运营服务 / 认证核查 / 培训宣传 / 其他 |
| `buyer` | string | 采购人 / 招标人 |
| `buyer_type` | enum | 政府机关 / 事业单位 / 国企 / 高校 / 上市公司 / 民企 / 其他 |
| `winner` | string? | 中标人 / 成交供应商（仅中标阶段有） |
| `amount_wan` | float? | 中标金额或预算金额，统一换算为**万元**；未披露为 null |
| `amount_raw` | string? | 原文金额表述（用于复核） |
| `region` | string | 省/直辖市（能到市则到市） |
| `publish_date` | string | 公告发布日期 YYYY-MM-DD |
| `deadline` | string? | 投标截止时间（招标公告才有） |
| `source_name` | string | 来源平台名 |
| `source_level` | int | 来源权威度 1/2/3（见 4.4） |
| `url` | string | 公告链接 |
| `summary` | string | 一句话摘要 |
| `collected_at` | string | 采集时间戳 |

### 4.2 SKILL.md 设计

**Frontmatter（触发机制）：**

```yaml
---
name: esg-bid-monitor
description: 汇总分析ESG/可持续发展/双碳领域的招投标与中标信息，并每日监控推送新增ESG招标。当用户要求分析过去一段时间（如2年）ESG/双碳/碳中和/绿色/可持续发展相关的中标情况、热点招标、中标金额分布、投标市场分析，或要求监控/跟踪/推送新的ESG相关招标信息、每日ESG标讯速递、帮我发现新投标商机时，务必使用本技能——即使用户没有明确说"投标分析"或"监控招标"。支持两种模式：回溯汇总模式（report，默认）与每日监控模式（monitor）。
argument-hint: "[模式: report|monitor] [时间范围，可选] [主题/地区，可选]"
---
```

> description 遵循 skill-creator 规范：定义域 + 双模式场景枚举 + "务必使用本技能——即使没明确说"的 pushy 措辞，覆盖"分析中标""金额分布""监控招标""每日推送"等多种自然说法，避免 undertrigger。

**正文结构（约 250~350 行）：**

1. **一句话定位**：双模式说明、数据落盘位置（对齐输出期望）；
2. **模式判定规则**（Phase 0）：`monitor`/监控/推送/今日 → monitor；`分析`/汇总/回顾/金额分布 → report；未指明默认 report；
3. **双模式工作流**（Phase 1~3）：每阶段为祈使句指令并说明 why（如"检索词分批并行发起以突破单次结果上限""指纹去重防止跨运行重复入库"）；
4. **读取指引**：Phase 1 前读 `search-playbook.md` + `keywords.md`；Phase 2 前读 `extraction-rules.md`；Phase 3 前按模式读 `analysis-guide.md` / `report-template.md`；
5. **状态管理规则**：每次运行结束更新 `state.json`（last_run、seen_count）；monitor 模式监测窗口 = 「近24h」与「自 last_run 以来」的并集（窗口起点取 min），刚跑过也至少回看 24h、漏跑多天自动回补；
6. **失败兜底**：某主题检索无结果 → 换词/换 site 补检一轮，仍无则如实标注"该主题公开可检索样本不足"；原文抓取失败 → 以搜索摘要入库并降低置信度标注；禁止对同一 URL 反复重试。

### 4.4 references/search-playbook.md 设计

**（1）数据源清单与权威度分级：**

| 级别 | 来源类型 | 代表站点 | 使用规则 |
|---|---|---|---|
| 一级（权威） | 国家级官方平台 | 中国政府采购网 ccgp.gov.cn、中国招标投标公共服务平台 cebpubservice.com、全国公共资源交易平台 | 直接采用，优先作为结构化数据主源 |
| 二级（可信） | 省市官方平台与主流媒体 | 各省/市公共资源交易中心、政府官网通知公告、新华社/证券时报等行业报道 | 采用；金额等关键数字尽量回溯一级源 |
| 三级（线索） | 商业聚合平台 | 千里马、采招网、剑鱼标讯、比地招标 | 仅作线索（多数有登录墙）；经搜索快照获取的信息入库时标注"待核实" |
| 三级（线索） | 企业自宣 | 中标企业官网/公众号中标喜报 | 用于补充中标人/金额，标注"企业自宣" |

**（2）检索词矩阵扇出策略（回溯模式）：**

- 按主题（5 类）× 阶段（招标公告/中标公告）切分为 **10 条主线**，每线 4~6 组检索词，同一批**并行发起**；
- 每组检索词轮换角度：泛搜（如 `双碳 中标公告 2025`）、site 限定（如 `site:ccgp.gov.cn 碳中和 成交`）、地区限定（如 `XX省 公共资源交易 碳 中标`）、年度限定（2024/2025/2026 各扫一遍）；
- 每条主线有效入库记录 ≥8 条为达标，不足则换词补检一轮；
- 检索笔记（关键词批次、命中数、代表链接）随时落盘 `data/notes/`，防止长会话上下文丢失。

**（3）监控模式检索策略：** 固定用"主题词 × 招标/采购 × 近24h/今日"组配 + 各官方平台 site 限定，一轮并行检索即可，重点保时效而非穷尽。

### 4.5 references/extraction-rules.md 设计

**（1）金额规范化表（统一换算为万元）：**

| 原文写法 | 解析结果 |
|---|---|
| 「中标金额：1,285,000 元」 | 128.5 |
| 「成交金额为 365.8 万元」 | 365.8 |
| 「中标价 1.2 亿元」 | 12000.0 |
| 「预算金额：450 万」 | 450.0（stage 仍为招标公告，字段标 budget） |
| 「最高限价 80 万元，未披露成交价」 | 80.0 + 备注为限价而非成交价 |
| 无金额 / 「具体面议」 | null + 标注「金额未披露」 |

**（2）去重指纹规则**：`record_id = sha1(规范化项目名 + 采购人)[:12]`，规范化 = 去空格/全半角统一/去括号补充说明；同指纹已存在时：stage 升级（招标→中标）则更新原记录的 stage/winner/amount，否则跳过；URL 相同亦判重。

**（3）字段抽取优先级**：公告正文 > 搜索摘要 > 标题；无法确认的字段置 null 而非猜测；每条记录必须带 url 与 publish_date，否则不入库。

### 4.6 references/analysis-guide.md 设计 —— 统计口径与图表规范

| 统计项 | 口径 |
|---|---|
| 样本口径 | 仅统计入库的结构化记录；报告明示总样本量 N、来源构成、按月覆盖情况 |
| 金额统计 | 基于 `amount_wan` 非空子集计算；同时披露缺失率；均值与中位数并列（防大单拉偏） |
| 金额分桶 | <50万 / 50–100万 / 100–500万 / 500–1000万 / 1000–5000万 / 5000万–1亿 / ≥1亿（单位：万元） |
| 热点排名 | 主题、项目类型、地区（Top10）、采购人类型、中标企业 Top10（次数+累计金额双指标） |
| 趋势 | 按发布月聚合 24 个月的条目数与金额合计，判断上升/波动 |
| 图表规范 | Markdown 报告内嵌 Mermaid（pie/bar/xychart）；HTML 增强版可调用 dataviz 技能获取配色与规范，生成带交互图表的静态页 |

`scripts/stats.py`（纯标准库）输入 `bids.jsonl`，输出 JSON：各主题计数、地区 Top10、月度序列、金额分桶分布、Top 中标企业、缺失率——供 Agent 直接引用，保证统计可复现、避免心算错误。

### 4.7 references/report-template.md 设计 —— 双模板

**（1）回溯报告固定结构：**

```markdown
# ESG/双碳领域招投标市场回顾报告（2024-11 ~ 2026-11）
样本说明：入库 N 条 | 来源构成 | 金额可解析率 | 免责声明

## 摘要（150~300 字）
## 核心发现速览（6~8 条要点 + 关键数字卡片）
## 一、市场总览（样本量、月度发布趋势图、来源与覆盖说明）
## 二、热点主题分析（主题分布图 + 各主题代表项目 + 为什么热）
## 三、中标金额分布（分桶直方图、总额/均值/中位数、Top10 大单表）
## 四、地域与采购人分析（省份 Top10 图、采购人类型分布、解读）
## 五、中标格局（中标企业 Top10 表、竞争集中度观察）
## 六、趋势研判与投标建议（未来热点方向、报价区间参考、市场进入建议）
## 附录（A 明细数据表节选 B 字段与口径说明 C 完整来源清单 D 局限性声明）
```

> 第六章"给投标企业的启示"是超出基本需求的加分项：将统计结论转化为可操作建议（如"100–500 万区间的咨询服务标的最多，可作为主攻价位带"）。

**（2）每日速递固定结构：**

```markdown
# ESG 标讯速递（YYYY-MM-DD）
今日新增 N 条 | 新招标 M 条 | 监测窗口：{起} ~ {止}
## 重点推荐（高金额 / 大客户 / 3 日内截止，3~5 条，逐条给关注理由）
## 新招标一览表（标题 | 采购人 | 地区 | 预算金额 | 截止时间 | 链接）
## 近期中标动态（昨日至今中标公告简表，供竞对跟踪）
## 提示（即将截止、预算异常、待核实条目说明）
```

**（3）质量自查清单**（成报后逐项核对）：样本量与口径已声明 / 金额缺失率已披露 / 每条记录有来源与日期 / 统计数字与 stats.py 输出一致 / monitor 日报中无已推送过的旧条目 / 附录来源 URL 完整。

## 五、每日监控与推送部署设计

| 环节 | 方案 |
|---|---|
| 增量窗口 | 窗口起点 = `min(近 24h 起点, last_run)`（两者并集），避免因漏跑丢失条目 |
| 去重 | 指纹库随 bids.jsonl 自然累积；日报只呈现未见过的条目 |
| 产出 | `data/daily/ESG标讯速递_YYYY-MM-DD.md`，同日重跑覆盖 |
| 推送（默认） | 落盘后向用户报告文件路径与要点摘要 |
| 推送（增强，可选） | 飞书/钉钉/企业微信机器人 webhook：日报转纯文本 POST；配置写入 `state.json` 的 `webhook` 字段 |
| 定时调度（生产） | crontab + Claude Code 无头模式：<br>`30 8 * * * cd /path/to/part2 && claude -p "使用 esg-bid-monitor 技能执行每日监控模式" --allowedTools "WebSearch WebFetch Read Write Bash" >> data/daily/cron.log 2>&1` |
| 定时调度（会话内演示） | `CronCreate`：`cron="43 8 * * *", recurring=true, prompt="使用 esg-bid-monitor 技能执行每日监控模式"`（注意：会话级任务随会话结束失效，7 天自动过期，长期运行须用 crontab/launchd） |

## 七、质量保障设计（回应"效果越好越好"）

| 抓手 | 具体机制 |
|---|---|
| 检索广度 | 10 条主线 × 每线 4~6 组检索词，泛搜/site/地区/年度四类角度轮换，并行发起；关键命中抓原文而非只看摘要 |
| 数据严谨 | 统一 JSONL 模型 + 金额规范化表 + 指纹去重 + 字段缺失置 null 不猜测；统计由脚本计算而非心算 |
| 口径诚实 | 样本边界、来源构成、金额可解析率、局限性声明全部写入报告——宁要"可核验的部分真实"，不要"看似全量的虚构" |
| 分析深度 | 不止罗列：热点主题解读为什么热、趋势研判、第六章转化为投标企业的可操作建议 |
| 结构可读 | 摘要 + 核心发现速览（30 秒读完）；Mermaid/HTML 图表；速递版"重点推荐"前置 |
| 过程可靠 | 检索笔记落盘防上下文丢失；主线数量下限不足自动补检；state.json 保证跨运行状态连续；兜底规则避免无效重试 |
| 收尾把关 | 成报后逐项跑质量自查清单，不合格先修复再交付 |

## 九、风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 商业标讯平台登录墙 | 无法直接抓取聚合站明细 | 以官方平台 + 搜索引擎为主源；聚合站仅取搜索快照作线索并标"待核实" |
| 两年历史公告无法穷尽 | 统计结论可能低估市场总量 | 多角度分批扇出扩大覆盖；报告明示"公开可检索样本"口径与月度覆盖分布，建议按主线补检 |
| 金额缺失率高 | 金额分布代表性下降 | 单列缺失率；分桶统计基于非空子集并注明；中位数与均值并列 |
| 一标多公告重复计数 | 热点/金额统计虚高 | 指纹去重 + stage 演化合并（招标→中标更新而非新增） |
| LLM 抽取错误（张冠李戴） | 中标人/金额错配 | 抽取规则强制"金额必须与中标人同段核实"；金额带 amount_raw 原文回查；报告抽查核对 |
| 搜索接口结果上限 | 单主题覆盖不足 | 批次化扇出、地区/年度切片检索；笔记记录各批次命中数 |
| 定时任务环境不可用 | 无人值守推送失效 | 提供 crontab/launchd 与会话内 CronCreate 两级方案；state.json 兜底补漏 |
