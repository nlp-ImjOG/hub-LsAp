# 作业2 分析文档：Skill 脚本沉淀与「有脚本 vs 无脚本」效果对比

> 需求原文（readme.txt）：
> 1. 尝试对做好的 skill 沉淀出一些 script；
> 2. 搜索互联网 + 内容总结可以通过高代码实现；
> 3. **对比如果 skill 有一些确定性的 script vs 没有任何 script 的效果对比。**

---

## 1. 需求解读

readme 三句话实际对应三件事，第 3 件（加粗）是本作业的核心交付：

| # | 任务 | 实质 | 交付物 |
|---|------|------|--------|
| A | 对做好的 skill 沉淀 script | 把作业1两个 skill 中"模型每次都在重复做的确定性动作"改写为可复用的 Python 脚本 | 新增 `scripts/*.py`，SKILL.md 改为"调脚本 + 做语义判断" |
| B | 搜索+总结的高代码实现 | 论证并实现"搜索互联网"环节的高代码管线（抓取、解析、去重、统计），明确哪些环节**不该**高代码化 | `search.py` 等检索/抽取管线脚本 |
| C | 有脚本 vs 无脚本对比 | 设计并执行 A/B 实验，用数据回答"确定性脚本对 skill 效果的影响" | 对比实验报告（指标表 + 结论） |

三件事的关系：A 是手段，B 是 A 中最难也最有代表性的切片（搜索环节），C 是验证 A/B 是否值得做的实验闭环。

## 2. 现状盘点：作业1 两个 skill 的脚本化程度

| Skill | 现有脚本 | 确定性动作现状 | 暴露的问题 |
|-------|---------|---------------|-----------|
| `esg-monthly-report`（月报） | **0 个**，纯 SKILL.md + 3 份 references | 检索词展开、时间窗过滤、来源分级、去重、统计、引用编号全部由模型临场执行 | 数字靠模型心算/转述；上下文压缩后笔记与统计易失真；每轮重跑检索词漂移 |
| `esg-bid-monitor`（标讯） | 1 个（`stats.py`，统计） | 抽取字段、金额换算万元、record_id 指纹去重、bids.jsonl/state.json 读写仍是模型手写 | 手写 JSONL 易出格式错；金额换算与指纹规则每次靠模型复述 `extraction-rules.md`，执行不稳定 |

**结论**：两个 skill 的"骨架"（流程编排、语义判断、写作）已由 SKILL.md 沉淀，但"肌肉"（确定性执行）大量依赖模型临场发挥——这正是作业2要抽出来的部分。

## 3. 哪些环节适合沉淀为脚本：判定标准

一条动作是否值得脚本化，用四条标准衡量（满足任意两条即倾向脚本）：

1. **规则可枚举**：逻辑能用 if/正则/查表完整表达（金额换算表、时间窗过滤、指纹规则）；
2. **对精确性敏感**：错一点就毁交付（统计数字、去重、引用编号一致性）；
3. **跨调用有状态**：需要稳定落盘/读盘（bids.jsonl、state.json）——模型每次"现场读现场写"不可靠；
4. **高频重复**：每次运行都做且做法相同（检索词扇出、结果解析）。

反之，**依赖语义理解与生成**的动作留给模型。

### 3.1 逐环节分类（基于作业1实际流程）

| 环节 | 作业1谁在做 | 是否脚本化 | 理由 |
|------|-----------|-----------|------|
| 报告期/参数解析（"近一个月""近2年"→具体日期区间） | 模型心算 | ✅ | 规则可枚举 + 精确性敏感，心算日期是典型错源 |
| 检索词扇出（词库 × 角度矩阵展开） | 模型读 playbook 展开 | ✅ | 查表逻辑，脚本展开可保证每轮词表一致、不漂移 |
| **搜索互联网（抓结果页/原文、HTML 解析、URL 归一化）** | 模型用 WebSearch/WebFetch | ✅（任务B核心） | 输入输出确定；高代码可控制重试、超时、去噪、并发 |
| 相关性初筛（关键词命中 + 黑名单词，如"绿色绿化带"误命中） | 模型逐条判断 | ⚠️ **分层**：规则层脚本（粗筛）+ 语义层模型（终判） | 字面巧合可枚举，"是否真与 ESG 相关"不可枚举 |
| 字段抽取（日期、金额、中标人、省份） | 模型读原文抽数 | ⚠️ **分层**：正则+换算表抽"硬字段"，抽不到的置 null 留给模型补 | 金额/日期正则可枚举且精确性敏感；"这家公司是不是中标人"是语义 |
| 金额规范化（口径区分 + 万元换算） | 模型按换算表心算 | ✅ | 教科书级"查表 + 算术"，心算错一个数量级整份报告报废 |
| 指纹去重（record_id 计算 + stage 升级合并） | 模型手写 JSONL | ✅ | 规则明确 + 跨调用状态，手写极易重复入库 |
| 数据库读写（bids.jsonl / state.json） | 模型手写 | ✅ | 状态管理必须代码化，行数复核/原子写都由脚本保证 |
| 统计分析（主题分布、金额分桶、Top10、月度趋势） | `stats.py`（已有） | ✅ 已沉淀 | 作业1已做对的部分，保留 |
| 报告骨架渲染（表格、Mermaid 图、附录来源清单） | 模型手写 Markdown | ⚠️ 可选 | 骨架可模板渲染，保证格式零错；正文分析仍模型写 |
| 质量自查（引用编号与附录一致、时间窗越界、字数下限） | 模型读 checklist 自查 | ✅ | "可执行的检查"代码化，比模型自查可靠 |
| 相关性终判、影响分析、趋势研判、报告写作 | 模型 | ❌ 不脚本化 | 开放语义生成，脚本只能做"抽取式总结"，写不出"影响点评" |

### 3.2 关于"内容总结"能否高代码

需求第 2 条说"搜索互联网 + 内容总结可以通过高代码实现"，需要拆开看：

- **搜索互联网**：可以完整高代码化——请求、解析、去噪、去重、入库，全部确定性管线；
- **内容总结**：只能**部分**高代码化。抽取式总结（按日期/金额/标题截取要点、关键词、首段规则）可代码化；但"这条政策对客户意味着什么"这种生成式总结，脚本做不了，这正是模型的价值所在。

这个不对称恰好构成第 5 章对比实验的核心假设：**确定性环节脚本化收益大，语义环节模型不可替代——最优解是混合架构**。

## 4. 脚本沉淀清单（计划产出）

新 skill 包 `.claude/skills/<name>/scripts/` 下计划沉淀（纯标准库，与 `stats.py` 风格一致）：

| 脚本 | 职责 | 来源环节 |
|------|------|---------|
| `parse_args.py` | 自然语言时间表达 → 精确日期区间；客户/行业参数解析 | 月报 Phase 0 |
| `search.py` | 检索词扇出 + 抓取搜索结果 + URL 归一化 + 原文抓取与正文去噪（无 API key 时以可配置的抓取端点/直访站点清单兜底） | 任务B核心 |
| `filter.py` | 规则层初筛：关键词命中、黑名单词、时间窗过滤，输出"待语义判定"清单 | 标讯 Phase 2.1 |
| `extract.py` | 硬字段抽取：日期/金额（含万元换算与口径区分）/中标人/省份，带置信度，抽不到置 null | 标讯 Phase 2.2-2.3 |
| `store.py` | record_id 指纹计算、bids.jsonl 增量入库与 stage 升级合并、state.json 读写、行数复核 | 标讯 Phase 2.4 + 状态管理 |
| `render.py` | 按模板渲染报告骨架：统计表格、Mermaid 图、附录来源清单自动生成 | 月报/标讯 Phase 3 |
| `check.py` | 质量自查可代码化项：引用编号↔附录一致性、报告期外数据检测、字数下限、文件齐套 | 两 skill 的自查清单 |
| `stats.py` | （已有，复用）统计分析 | 标讯 Phase 3 |

改造后的 SKILL.md 分工变为：**脚本管"做对"，模型管"做好"**——模型不再手写 JSONL、不再心算金额，只做语义判定与写作，并通过脚本输出（JSON）获得可靠的中间结果。

## 5. 对比实验设计（作业核心）

### 5.1 实验对象与分组

| 组 | 配置 | 说明 |
|----|------|------|
| **A 组（基线）** | 作业1 `esg-monthly-report` 原样：零脚本，纯提示词 | 天然的"无 script"对照组，无需重写 |
| **B 组（实验）** | 第 4 章脚本沉淀后的 skill：管线动作全部走脚本，模型只做语义判定与写作 | "有确定性 script"实验组 |

### 5.2 任务与控制变量

- **统一任务**：`生成中国神华 2026-11 ESG月报`（A/B 各跑）；标讯 skill 另跑一组 `汇总近2年ESG中标` 用于验证数据管线类任务。
- **控制变量**：同一模型、同一天执行、同一报告模板与输出路径规范、**固定检索预算**（限定检索/抓取次数上限，防止 B 组靠堆轮次换质量）。
- **重复次数**：每组各跑 **3 次**，取均值与极差——单次对比噪声太大，稳定性本身就是脚本化的卖点。

### 5.3 评测维度

**① 客观硬指标（脚本应赢的）**

| 指标 | 测法 | 预期方向 |
|------|------|---------|
| 数字准确率 | 报告中统计数字 vs 脚本口径重算结果 | B 显著优（A 靠模型心算/转述） |
| 金额换算错误数 | 抽查报告中金额与原始公告比对 | B 接近 0 错 |
| 去重正确性 | 入库重复记录数 / 误合并数 | B 显著优 |
| 来源可核验率 | 附录 URL 抽查 HTTP 200 率、日期与内容匹配率 | B 优（抓取管线带校验） |
| 引用一致性 | 正文 [n] 与附录清单一一对应检查（`check.py` 可直接测） | B 优 |
| 总耗时 / 检索轮次 / token 消耗 | 会话日志统计 | B 优（省去模型现场推规则的开销） |
| 重跑一致性（3 次方差） | 同任务 3 次产出的条目重合度、数字一致性 | B 显著优 |

**② 主观质量指标（模型主导的）**

| 指标 | 测法 |
|------|------|
| 结构完整性、分析深度（"对客户影响"点评质量）、建议可落地性 | 5 分制打分；由未参与实现的评审（人或 LLM-as-judge）盲评，隐去组别 |

**③ 需要警惕的反向指标**

- B 组是否因规则层过死而**漏检**（规则初筛误杀语义相关条目）→ 统计"入选条目数 / 信息覆盖面"，A 组不应显著更高；
- B 组脚本的维护成本与适应性：换客户/换行业时脚本是否需要改（对比 A 组提示词即插即用）。

### 5.4 预期结果与结论框架

| 维度 | 预期 | 机理 |
|------|------|------|
| 确定性指标（数字/去重/引用/一致性） | B ≫ A | 规则执行一次写对 vs 每次临场发挥 |
| 效率（耗时/token） | B > A | 省去"读规则→理解→执行"的重复开销 |
| 语义指标（分析深度/写作） | A ≈ B | 都由同一模型生成，脚本不直接增益 |
| 灵活性 | A > B | 提示词改一句话即可，脚本改动需开发 |
| 信息覆盖 | A ≈ B（需实测） | 取决于规则初筛的误杀率 |

**预期结论**：脚本化的价值不在"写得更好"，而在"每次都做对、做得快、可复跑"；确定性环节脚本化 + 语义环节留给模型的**混合架构**优于两个极端（纯提示词 / 纯高代码）。若实测语义指标 B 反而下降，检查规则层是否过死，属于工程问题而非架构问题。

### 5.5 交付物清单

1. 沉淀后的 skill 包（scripts + 改版 SKILL.md）；
2. `对比实验报告.md`：两组各 3 次运行的原始产物 + 5.3 指标表 + 结论；
3. 保留 A 组原 skill 不动，保证实验可复现。

## 6. 风险与边界

- **搜索高代码的可行性依赖环境**：无搜索 API key 时，抓取搜索结果页可能被反爬/改版。对策：`search.py` 设计为"可配置端点 + 直访权威站点清单"双路兜底，并把失败显式上报而非静默编造——这条纪律从作业1的 SKILL.md 延续下来。
- **脚本不是越多越好**：只沉淀满足 3 章四条标准的环节；把语义动作硬塞进脚本（如用关键词匹配假装"影响分析"）会降低质量。
- **公平性**：对比时给 A 组同样的检索预算与模板，否则结论会被"工具差异"污染。
- **范围控制**：以月报 skill 为主线（A/B 对比干净），标讯 skill 的 `store.py/extract.py` 作为数据管线脚本的补充验证，不追求两个 skill 全量改造。
