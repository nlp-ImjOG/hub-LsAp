### 1.2 总体数据流

```
用户输入 ──► parse_args.py ──► meta.json（客户/行业/日期区间）
                                     │
             search.py plan ──► queries.json（检索词扇出）
             search.py run  ──► results.json（候选：url/title/snippet/日期线索）
             search.py fetch-batch ──► pages.json（原文正文）
                                     │
             filter.py ──► filtered.json（passed=待语义终判 / rejected=带 reason_code）
                                     │
     模型语义终判（相关吗？值得写吗？）──► selected.json + 笔记
                                     │
     模型撰写分析段落 ──► render.py ──► report.md 骨架（引用编号自动分配）
                                     │
             check.py ──► check.json（error→必须修复后重跑）
```

分工边界一句话：**脚本输出"事实与结构"，模型消费脚本输出做"判断与表达"；模型不再手算、不再手写 JSONL、不再手工编号引用。**

## 2. 核心数据契约（脚本间 JSON 接口）

所有脚本输出 JSON 到 stdout（`--out` 可落盘），schema 如下。**这是脚本层与模型层唯一的握手方式**，模型只读这些字段。

```jsonc
// candidate：search.py run 的输出单元
{
  "qid": "A1",                    // 检索词批次号
  "line": "A",                    // A/B/C 三线（月报）或主题线（标讯）
  "url": "https://...",           // 原始 URL
  "norm_url": "https://...",      // 归一化后（去 utm/fragment/尾斜杠/http统一）
  "title": "...",
  "snippet": "...",
  "date_hint": "2026-11-03|null", // 摘要中抓到的日期线索，抓不到为 null
  "source_host": "www.csrc.gov.cn",
  "backend": "ddg|api|direct"
}

// page：search.py fetch 的输出单元
{ "url": "...", "final_url": "...", "http_status": 200, "ok": true,
  "title": "...", "text": "纯文本正文（去导航/脚本/广告）",
  "fetched_at": "ISO8601", "error": "null|超时|DNS失败|反爬403..." }

// filter.py 输出
{ "passed":   [ {candidate, "filter_notes": ["命中主题:ESG", "日期在窗内"]} ],
  "rejected": [ {candidate, "reason_code": "dup_url|dup_title|out_of_window|keyword_miss|blacklist_hit", "detail": "..."} ],
  "stats": { "total": 120, "passed": 38, "rejected": 82, "by_reason": {...} } }

// record：extract+store 后的标讯记录（18 字段模型，对齐作业1 extraction-rules.md）
{ "record_id": "sha1[:12]", "project_name": "...", "stage": "中标公告",
  "theme": ["双碳"], "industry_type": "咨询服务", "buyer": "...", "buyer_type": "国企",
  "winner": "...", "amount_wan": 128.5, "amount_raw": "中标金额：1,285,000 元",
  "region": "北京市", "publish_date": "2026-11-03", "deadline": null,
  "source_name": "中国政府采购网", "source_level": 1, "url": "...",
  "summary": "...", "collected_at": "ISO8601" }

// check.py 输出
{ "passed": false, "failures": [
    { "rule": "R1", "severity": "error",   // error→exit 1；warn→仅提示
      "detail": "正文引用 [7] 在附录清单中不存在", "line": 42 } ] }
```

## 3. 脚本详细设计

### 3.1 `parse_args.py` — 参数与日期解析（M1）

```
用法: python parse_args.py [--today YYYY-MM-DD] [--client 中国神华] [--mode monthly|report|monitor]
                          [--period "近一个月"|"2026-11"|"近2年"|"2026-01-01至2026-06-30"] [--out meta.json]
```

- 时间表达规则表：`近一个月`→today−30d；`近2年`→today−730d；`YYYY-MM`→当月起止；`A至B`→闭区间；缺省按 mode 取默认。
- 客户→行业查表（`中国神华→煤炭/传统能源`）；查不到输出 `"industry": null` 并在 stdout 提示"需模型检索确认行业"，**不猜**。
- 输出 `meta.json`：client / industry / today / start_date / end_date / period_label（`2026年11月刊`）。
- `--today` 参数专为测试存在：让日期逻辑对固定锚点可断言。

### 3.2 `search.py` — 搜索互联网高代码管线（M2，任务B核心）

四个子命令：

| 子命令 | 职责 |
|--------|------|
| `plan` | 读词库配置，按 `{线别×角度}` 矩阵扇出生成 queries.json（`{年}` 占位替换、site: 限定标注、同角度近义词只取一组） |
| `run` | 执行检索 → 解析结果页 → 输出 candidates（含 URL 归一化、结果内按 norm_url 去重） |
| `fetch` | 抓单 URL → 正文抽取 |
| `fetch-batch` | 并发抓一批（线程池 ≤4，单 URL 超时 15s，失败重试 1 次换 UA） |

**后端降级链**（`--backend auto` 按序探测，每个后端独立可配）：
1. `api`：环境变量 `SEARCH_API_URL` + `SEARCH_API_KEY`（兼容博查/Tavily/SerpAPI 类通用 JSON 格式）；
2. `ddg`：DuckDuckGo HTML 端点（html.duckduckgo.com/html/?q=），urllib + 正则/HTMLParser 解析，无需 key；
3. `direct`：直访站点清单兜底——作业1 playbook 第 4 节的站点表落成 `references/sites.json`，脚本抓站点搜索/列表页解析链接。

**正文抽取**（fetch）：stdlib `HTMLParser` 自实现——剔除 script/style/nav/footer/aside，保留 h1 与正文块，长度 <200 字符判"抽取失败"记 error。禁 JS 渲染站点失败属预期，输出 `ok:false` 由上层换源，**不静默编造**。

**缓存**：`data/cache/<sha1(norm_url)>.json`，会话内同 URL 不二次抓取（省钱省时，也是 A/B 实验公平性的一部分）。

**URL 归一化规则表**（parse 阶段执行）：去 `utm_*/spm/from` 参数 → 去 fragment → `http→https` → 去尾斜杠 → 解包搜索引擎跳转链 → 大小写归一 host。

### 3.3 `filter.py` — 规则层初筛（M1）

```
用法: python filter.py --input results.json --window "2026-10-25:2026-11-24"
                       [--mode monthly|bid] [--keywords keywords.json] [--out filtered.json]
```

顺序执行的规则链，**每条拒绝必须带 reason_code，绝不静默丢弃**：

1. 去重：norm_url 相同 → `dup_url`；标题归一化（去空格标点）哈希相同 → `dup_title`；
2. 时间窗：date_hint 明确落在窗外 → `out_of_window`；**日期缺失 → 保留并标 `date_unknown`**（留给模型判，不误杀）；
3. 主题词命中：mode=bid 用 keywords.md 五大主题表；mode=monthly 用 playbook 三线词库的宽松匹配；
4. 黑名单巧合词（mode=bid）：标题命中"绿色通道/绿化带/绿色食品"等且无强主题词 → `blacklist_hit`（对齐作业1"典型排除项"清单）。

`passed` 的语义是**待模型语义终判的清单**，不是最终入选——这是"分层"设计的落点。

### 3.4 `extract.py` — 硬字段抽取（M4，标讯）

对齐作业1 `extraction-rules.md`，脚本只抽数值/枚举类"硬字段"，语义字段置 null 留模型：

| 字段 | 方法 | 置信度规则 |
|------|------|-----------|
| publish_date | 发布日期正则族（`发布时间：`/`Date:`/ISO/中文日期） | 命中即 high |
| amount_wan | 金额正则 + 单位换算表（元÷1e4、亿×1e4）+ 口径识别（成交/中标价 > 预算 > 最高限价） | **金额与中标人同一句内出现才 high**（对齐"金额必须与中标人同段核实"）；否则 medium/null |
| winner | `中标供应商/中标人/成交供应商` 正则，仅成交侧 stage | low→置 null 留模型 |
| stage / theme | keywords.md 阶段词表 / 五大主题多标签匹配 | high |
| region | 省份+直辖市词表匹配 | high |
| project_name / buyer | 标题切分启发式（"XX项目"截取、"采购人："捕获） | low→null 留模型 |

输出每条：`{"fields": {...}, "confidence": {...}, "needs_model": ["winner","buyer"]}`——模型只需处理 `needs_model` 列表，工作量显式量化。

### 3.5 `store.py` — 指纹去重与状态管理（M4）

```
用法: python store.py add    --db data/bids.jsonl --input records.json [--out result.json]
      python store.py seen   --db data/bids.jsonl --out seen.json     # 读基线指纹集合
      python store.py state  --file data/state.json [--set-last-run] [--add-daily-log]
```

- 指纹 = `sha1(规范化项目名 + buyer)[:12]`，规范化 = 去空格、全半角统一、去括号补充说明（与 extraction-rules.md 逐字一致）；**norm_url 相同亦判重**。
- 已存在指纹：stage 升级（招标公告 < 更正公告 < 中标公告/成交结果/入围公示）→ 更新原行 stage/winner/amount_wan；同级 → skip。
- 写入策略：整库读入内存 → 合并 → **原子写**（写 tmp + `os.replace`）；输出 `{"added":n,"updated":m,"skipped":k,"lines":N}` 供笔记复核（"边采边入库"纪律改由脚本保证）。
- `state.py` 职责并入本脚本（读写 state.json：last_run / seen_count / daily_log，保持 seen_count == 行数）。

### 3.6 `render.py` — 报告骨架渲染（M3）

```
用法: python render.py monthly --template references/report-template.md --meta meta.json
                               --sources sources.json --selected selected.json --out report.md
      python render.py bids    --stats stats.json --sources sources.json --out report.md
```

- **月报**：按模板生成章节骨架，分析段落留 `<!-- 模型撰写：对本节主题，写对客户的影响点评 -->` 占位；自动生成：封面信息块（客户/行业/报告期）、三线入选统计表、**附录 A 来源清单**（按引用顺序自动编号 [1..n]）。
- **引用自动编号**：模型正文写 `{{cite:norm_url}}` 占位 → render 替换为 [n] 并同步生成附录——从机制上消灭作业1"手工编号错位"错型。
- **标讯**：stats.json → Markdown 表格 + Mermaid 图自动渲染（主题分布 pie / 月度趋势折线 / 省份 Top10 柱状 / 金额分桶柱状），Mermaid 语法规则代码化，保证图必可渲染。

### 3.7 `check.py` — 可代码化质量自查（M1）

```
用法: python check.py report --file report.md --window "start:end" [--min-words 300] [--out check.json]   # exit 0/1
      python check.py db     --db data/bids.jsonl [--out check.json]
```

| 规则 | 内容 | 级别 |
|------|------|------|
| R1 | 引用一致性：正文 [n] ⊆ 附录且附录编号连续；附录未被引用项 → warn | error |
| R2 | 时间窗越界：报告期外日期未带"数据日期"标注 | error |
| R3 | 占位残留：`<!-- 模型撰写 -->` / TODO 未清除 | error |
| R4 | 各章字数下限 | error |
| R5 | 空章节 / 表格空行 / Mermaid 代码块存在但为空 | warn |
| R6 | 产物文件齐套（report + notes 存在） | error |
| R7 | db 模式：18 字段必填非空、日期格式、指纹唯一、行数 == seen_count | error |

**该脚本对 A/B 两组通用**——评测时对 A 组（无脚本版）产出同样跑 check.py，这是对比公平性的关键工具。

## 4. SKILL.md 改版要点（B 组编排）

| Phase | 作业1（A组，模型执行） | B组（脚本执行） |
|-------|----------------------|----------------|
| 0 输入解析 | 模型心算日期区间 | `parse_args.py` 产出 meta.json，模型读它 |
| 1 信息采集 | 模型读 playbook 现场组词、WebSearch/WebFetch、凭记忆记笔记 | `search.py plan`→`run`→`fetch-batch`，产物全部落盘 JSON；模型只**阅读结果挑发现** |
| 2 筛选 | 模型逐条判断 | `filter.py` 规则初筛 → 模型只对 `passed` 清单做语义终判，写笔记 |
| 3 成报 | 模型手写全文含引用编号 | 模型写分析段落（`{{cite:url}}` 占位）→ `render.py` 骨架合成 → `check.py` 自查，error 必须修复 |
| 兜底 | "检索工具不可用即告知用户，不编造" | 延续：search.py `ok:false` → 换词/换 backend/直访 sites.json，不编造 |

改版原则：SKILL.md 的篇幅重心从"怎么做检索、怎么换算金额"（规则细节已进脚本）转移到"怎么判断与写作"，规则类 references（search-playbook 中的词库、extraction-rules 中的换算表）转化为脚本的数据配置文件（keywords.json / sites.json）。

## 5. 测试方案与效果验证步骤（四层）

### T1 单元测试（离线，无网络，确定性）

**方式**：stdlib `unittest`，每脚本一个 `tests/test_*.py`；一切依赖"今天"的逻辑通过 `--today` 固定锚点断言；网络层全部用 `tests/fixtures/` 里**预先录制的响应样本**驱动，测试永不联网。

**各脚本关键用例**：

| 测试文件 | 必覆盖用例 |
|----------|-----------|
| test_parse_args | 近一个月/近2年/显式YYYY-MM/A至B区间/跨月边界；行业查表命中与 null 不猜 |
| test_search | 录制结果页 fixture 的解析正确性；URL 归一化 8 条规则逐条断言；重复 URL 去重；fetch 对畸形 HTML（script 混正文）的抽取；`ok:false` 不抛异常 |
| test_filter | "绿色绿化带"黑名单排除；时间窗边界（窗内最后一天/窗外第一天）；date_unknown 放行；dup_url/dup_title |
| test_extract | extraction-rules.md 金额换算表 7 个用例**逐条照抄为断言**（元→128.5、亿→12000、折扣率→null…）；口径优先级；金额-中标人同段 high / 分段 null |
| test_store | 新增/同 stage 跳过/stage 升级更新；同名项目不同 buyer 不碰撞；state.json 更新与 seen_count 一致；原子写中断不损坏原库 |
| test_render | golden-file：骨架与附录编号快照对比；`{{cite}}` 多次引用同 URL 编号不重复；Mermaid 图语法快照 |
| test_check | 每条规则 R1–R7 各构造 1 正 1 反用例（含故意写错的报告样本） |

**运行**：`python -m unittest discover -s tests -v`，全绿为 M1–M4 各里程碑的验收门槛。

### T2 集成冒烟（离线，全管线）

用 `tests/fixtures/` 中 10 条模拟公告/新闻文本（含 2 条故意放的黑名单巧合、3 条重复、2 条窗外）：

1. 手动以 file:// 缓存模式驱动 `search.py fetch`（或直接从 pages.json 起步）；
2. 依次执行 filter → extract → store → stats → render → check 全链；
3. 断言：重复 3 条全被 `dup_*` 拒绝、黑名单 2 条被 `blacklist_hit` 拒绝、窗外 2 条被拒、入库行数 == 预期、check.py 通过。
（复用作业1 part2 `tests/test_skill_demo.py` 的 mock 驱动模式。）

### T3 真实联网冒烟（单次、小预算，验证"搜索高代码可行"假设）

1. `search.py plan` 生成 6 组检索词 → `run --backend auto`；
2. 人工抽查指标：返回结果 URL 打开率 ≥70%、date_hint 命中率 ≥50%、单批耗时 ≤60s；
3. 不达标 → 调整后端顺序 / UA / 超时，必要时把该后端标记禁用（写入配置而非删代码）；
4. 记录本次后端命中情况到 `tests/联调记录.md`，作为实验环境基线。

### T4 A/B 对比实验（作业核心交付，操作步骤）

**Step 1 准备**
- A 组 = 作业1 `esg-monthly-report` 原样；B 组 = 本次 `esg-monthly-report-scripted`；
- 统一任务话术：`/esg-… 生成中国神华 2026-11 ESG月报`；统一模板与输出路径规范；
- 统一预算：每次运行检索+抓取 ≤30 次（两个组都在任务话术中声明，防 B 组靠堆轮次换质量）。

**Step 2 执行**
- 每组各跑 **3 次**（独立会话，A/B 交替执行避免环境漂移）；
- 每次落盘 `runs/{A,B}组_第{n}次/`：完整产物（report/notes）+ 会话 transcript + 起止时间与工具调用次数。

**Step 3 指标采集**（`tests/evaluate.py` 半自动 + 人工抽查）
- 客观：`check.py` 对**两组**报告统一跑（R1/R2/R3 错误数）；附录 URL 批量 HEAD 探活 → 可核验率；transcript 统计耗时/轮次/token；重跑一致性 = 3 次入选条目标题集合的 Jaccard 相似度；
- 数字准确率：每组随机抽 10 个报告数字，回溯其来源 URL 人工比对，记录错数；
- 主观：两组报告**匿名化**（去路径/组别痕迹）后，由未参与的评审（或 LLM-as-judge）按 5 分制盲评：结构完整性 / 分析深度 / 建议可落地性。

**Step 4 汇总**
- 按 `作业2_分析文档.md` 5.3 的指标表填数，产出 `对比实验报告.md`：数据表 + 与预期方向（5.4 节）的吻合度 + 结论（混合架构是否成立）；
- 若 B 组语义指标反而下降 → 按分析文档的预案归因到规则层过死（工程问题），在报告中单列。

## 6. 风险与对策

| 风险 | 对策 |
