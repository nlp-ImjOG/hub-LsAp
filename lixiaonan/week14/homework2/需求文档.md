## 1. 项目概述

### 1.1 项目背景

传统 RAG（Retrieval-Augmented Generation，检索增强生成）问答系统主要面向纯文本场景，对 PDF 等富格式文档中的图片、表格、公式等非文本内容支持不足，且回答只能以纯文字呈现。本项目旨在**基于 Kafka** 复刻一套多模态 RAG 问答系统的完整实现，重点解决两个问题：

1. **文档解析的异步化与可观测性**：通过 Kafka 将「上传」与「解析」解耦，解析任务异步执行，解析状态实时可查；
2. **问答的多模态化**：检索结果与用户输入均支持图片，回答支持图文混排。

### 1.2 项目目标

- 用户通过前端网页批量上传 PDF 文档；
- 后端通过 Kafka 异步分发解析任务，使用 MinerU 完成 PDF 解析并落库存储；
- 前端实时展示每个文档的解析状态（待解析 / 解析中 / 解析完成）；
- 用户发起提问时，支持携带图片（图文一起提问），检索命中的图片与文本一起送入多模态 LLM，回答支持图文混排展示。

### 1.3 名词解释

| 术语 | 说明 |
| --- | --- |
| MinerU | 开源 PDF 解析工具，可将 PDF 转换为 Markdown，并抽取其中的图片、表格等内容 |
| Kafka | 分布式消息队列，本项目用于解耦文档上传与解析流程，实现削峰填谷 |
| RAG | 检索增强生成：先从知识库检索相关内容，再交给 LLM 生成回答 |
| 多模态 LLM | 支持同时理解文本与图片输入的大语言模型（如 Qwen-VL、GLM-4V、GPT-4o 等） |
| 图问 | 用户提问时附带图片作为问题的一部分 |
| 图文混排 | LLM 的回答中同时包含文字与图片，前端按 Markdown 渲染 |
| Embedding | 将文本/图片编码为向量，用于语义检索 |
| 向量库 | 存储向量并支持相似度检索的数据库（如 Milvus、Qdrant、FAISS） |

## 2. 系统总体架构

### 2.1 架构图

```
┌─────────────┐   HTTP    ┌──────────────────┐        ┌───────────────────┐
│   前端 Web   │ ────────► │   后端 API 服务    │──────► │  MySQL / SQLite    │
│  (上传/问答)  │ ◄──────── │  (FastAPI/Flask)  │        │  (文档/任务元数据)   │
└─────────────┘  轮询/SSE  └───────┬──────────┘        └───────────────────┘
                                  │ 1. 保存原始 PDF
                                  ▼                    ┌───────────────────┐
                          ┌───────────────┐            │  对象存储 / 本地磁盘 │
                          │    Kafka      │            │  (PDF 原件、图片)   │
                          │ pdf-parse-task│            └───────────────────┘
                          └───────┬───────┘
                                  │ 2. 消费解析任务
                                  ▼
                          ┌──────────────────┐
                          │   解析 Worker     │
                          │  (MinerU 解析)    │
                          └───────┬──────────┘
                        3.写入解析产物 │
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
        ┌──────────┐   ┌──────────┐    ┌──────────────┐
        │  向量库   │   │ 对象存储  │    │  MySQL/SQLite │
        │ (文本/图片 │   │ (图片文件) │    │  (解析结果/状态)│
        │  向量+描述)│   │          │    │               │
        └──────────┘   └──────────┘    └──────────────┘

问答链路：用户问题(+图片) ──► 检索服务 ──► 向量库召回文本块+图片
                                        └──► 多模态 LLM ──► 图文混排回答 ──► 前端
```

### 2.2 核心数据流

1. **上传链路**：前端上传 PDF → 后端保存原件 → 写入任务记录（`待解析`）→ 发送 Kafka 消息 → 200 返回前端。
2. **解析链路**：Worker 消费 Kafka 消息 → 更新状态为 `解析中` → MinerU 解析 → 文本块向量化入库、图片入对象存储（+可选生成图片描述）→ 更新状态为 `解析完成`（失败则 `解析失败` 并记录原因）。
3. **问答链路**：用户问题（文本 + 可选图片）→ 问题向量化 → 向量库召回 Top-K 文本块与图片 → 组装多模态 Prompt → LLM 生成 Markdown 回答 → 前端渲染图文混排结果。

## 3. 功能需求

### 3.1 功能 1：PDF 批量上传与异步解析

#### 3.1.1 需求描述

前端网页支持一次上传**多个 PDF 文件**，文件经后端保存后，通过 Kafka 投递解析任务，后端解析服务（Worker）调用 MinerU 完成 PDF 解析，并将解析产物持久化存储。

#### 3.1.2 功能点拆解

| 编号 | 功能点 | 说明 |
| --- | --- | --- |
| F1-1 | 多文件选择 | 上传控件支持多选 PDF，同时支持拖拽上传 |
| F1-2 | 文件校验 | 仅接受 `.pdf`；单文件大小上限默认 50MB（可配置）；单次上传数量上限默认 10 个（可配置） |
| F1-3 | 原件存储 | 后端将 PDF 原件保存到对象存储（MinIO）或本地磁盘，文件名使用 UUID 防冲突，保留原始文件名做展示 |
| F1-4 | 任务落库 | 每个文件生成一条解析任务记录，初始状态 `待解析` |
| F1-5 | 消息投递 | 后端向 Kafka Topic `pdf-parse-task` 发送消息；发送成功才视为上传成功，失败则任务标记 `解析失败` 并提示用户 |
| F1-6 | 任务消费 | Worker 订阅 `pdf-parse-task`，手动提交 offset，**消费失败可重试**，重试超过上限（默认 3 次）后标记失败 |
| F1-7 | MinerU 解析 | Worker 下载 PDF 原件，调用 MinerU 解析，产出：① Markdown 文本 ② 图片文件 ③ 版面/表格等结构信息 |
| F1-8 | 产物存储 | ① 文本按段落/分块向量化后写入向量库；② 图片写入对象存储，并将「图片 URL + 所在上下文 + 可选的图片描述（由多模态模型生成）」向量化写入向量库；③ 解析后的 Markdown、元数据写入关系库 |
| F1-9 | 重复处理 | 同一文件（按文件内容 hash 判重）重复上传时给出提示，是否允许重复入库由配置决定 |

#### 3.1.3 消息格式（`pdf-parse-task`）

```json
{
  "task_id": "uuid-string",
  "file_id": "uuid-string",
  "file_name": "示例文档.pdf",
  "storage_path": "minio://bucket/xxx.pdf 或 /data/uploads/xxx.pdf",
  "file_hash": "sha256-hex",
  "retry_count": 0,
  "created_at": "2026-11-10T12:00:00+08:00"
}
```

### 3.2 功能 2：解析状态展示

#### 3.2.1 需求描述

前端网页展示已上传文档的解析状态，状态包括：**待解析、解析中、解析完成**；扩展增加 **解析失败**（含失败原因），以便用户感知异常。

#### 3.2.2 状态机

```
 待解析 ──► 解析中 ──► 解析完成
   │          │
   │          └──► 解析失败（重试耗尽 / MinerU 异常 / 文件损坏）
   └────────────┘（消息发送失败、下载失败）
```

| 状态 | 编码 | 触发时机 |
| --- | --- | --- |
| 待解析 | `PENDING` | 上传成功、消息已入 Kafka 队列，尚未被消费 |
| 解析中 | `PARSING` | Worker 消费到消息并开始解析 |
| 解析完成 | `SUCCESS` | 解析产物全部入库成功 |
| 解析失败 | `FAILED` | 重试耗尽、MinerU 异常、文件损坏等，需记录失败原因 |

#### 3.2.3 功能点拆解

| 编号 | 功能点 | 说明 |
| --- | --- | --- |
| F2-1 | 状态列表 | 展示文件名、大小、上传时间、状态、失败原因（如有）、解析耗时 |
| F2-2 | 状态刷新 | 默认前端每 3 秒轮询一次；进阶要求改为 SSE/WebSocket 由后端推送（见 §7 开放问题） |
| F2-3 | 状态一致性 | 状态更新必须以数据库为准；Worker 「先置 PARSING，成功置 SUCCESS，失败置 FAILED」，保证任一时刻状态可恢复 |
| F2-4 | 边界兜底 | 任务长时间停留在 `PARSING`（超过可配置阈值，默认 30 分钟）时，由定时任务标记为失败并重新入队（可选） |
| F2-5 | 操作入口 | 支持查看解析结果（Markdown 预览）；支持对失败任务手动重新解析（可选） |

### 3.3 功能 3：多模态问答

#### 3.3.1 需求描述

用户在前端输入问题，可**附带图片**（图问）。系统检索知识库得到相关文本块与图片，与用户问题（含用户上传的图片）**一起送入多模态 LLM** 生成回答；回答支持**图文混排**（文字 + 图片按 Markdown 渲染）。

#### 3.3.2 功能点拆解

| 编号 | 功能点 | 说明 |
| --- | --- | --- |
| F3-1 | 提问输入 | 文本框输入问题（必填），支持附 0~N 张图片（默认 ≤3 张，单张 ≤10MB，格式 jpg/png/webp）；图片随问题一并送入 LLM |
| F3-2 | 知识库选择 | 可指定在「全部文档」或「选中文档」范围内问答（按上传的文档过滤检索） |
| F3-3 | 检索召回 | 问题文本向量化后在向量库检索，召回 Top-K（默认 K=5）文本块与图片；图片召回依据：图片描述向量 + 图片周边上下文文本 |
| F3-4 | 图文送 LLM | 组装多模态 Prompt：系统提示词 + 召回文本块 + 召回图片（base64/URL 形式）+ 用户问题 + 用户图片，调用多模态 LLM |
| F3-5 | 图文混排输出 | 要求 LLM 以 Markdown 输出；回答中引用的图片使用 Markdown 图片语法（指向对象存储 URL）；前端渲染 Markdown，图片正常显示 |
| F3-6 | 来源引用 | 回答中标注引用来源（文档名 + 位置），便于溯源；鼠标悬停/点击可查看原文（可选） |
| F3-7 | 会话管理 | 支持多轮对话（保留最近 N 轮上下文）；历史会话列表（可选） |
| F3-8 | 流式输出 | 回答以流式（SSE）方式返回，提升体验（可选） |

#### 3.3.3 问答时序

```
前端 ──(问题+图片)──► 后端问答接口
        │ 1. 图片暂存/转存
        │ 2. 问题向量化
        │ 3. 向量库检索 ──► Top-K 文本块 + 图片
        │ 4. 组装多模态消息
        ▼
      多模态 LLM ◄── 召回图片 + 用户图片 + 文本上下文
        │ 5. 生成 Markdown 回答（含图片引用）
        ▼
前端 ◄──(SSE 流式返回)── 后端：渲染图文混排回答 + 来源列表
```

## 4. 数据模型设计

### 4.1 文档表 `document`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string (UUID) | 主键 |
| file_name | string | 原始文件名 |
| file_hash | string | SHA-256，用于判重 |
| storage_path | string | 原件存储位置 |
| size | long | 文件字节数 |
| status | enum | `PENDING / PARSING / SUCCESS / FAILED` |
| fail_reason | text | 失败原因 |
| markdown_path | string | MinerU 产出的 Markdown 存储位置 |
| created_at / updated_at | datetime | 创建/更新时间 |

### 4.2 分块表 `chunk`（文本块 + 图片）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string (UUID) | 主键 |
| document_id | string | 所属文档 |
| chunk_type | enum | `TEXT / IMAGE` |
| content | text | 文本内容；图片则为「描述 + 周边上下文」 |
| image_url | string | 图片存储地址（IMAGE 类型） |
| page_no | int | 所在页码 |
| vector_id | string | 向量库中对应的向量 ID |
| created_at | datetime | 创建时间 |

### 4.3 会话与消息表（问答，可选）

- `conversation`：id、title、created_at
- `message`：id、conversation_id、role（user/assistant）、text_content、image_urls、citations（JSON）、created_at

## 5. 接口设计（REST API 草案）

| 方法 | 路径 | 说明 | 请求 | 响应 |
| --- | --- | --- | --- | --- |
| POST | `/api/documents/upload` | 批量上传 PDF（multipart） | files[] | 各文件的 id、file_name、status=`PENDING` |
| GET | `/api/documents` | 文档列表（含解析状态） | 分页参数、status 过滤 | 文档列表 |
| GET | `/api/documents/{id}` | 文档详情与状态 | - | 文档详情（含 fail_reason） |
| GET | `/api/documents/{id}/markdown` | 查看解析后的 Markdown | - | Markdown 内容 |
| POST | `/api/documents/{id}/reparse` | 失败任务重新解析（可选） | - | 任务状态 |
| POST | `/api/chat` | 多模态问答 | `{ "query": "...", "image_ids"/"base64": [...], "document_ids": [...] }` | SSE 流式：回答文本 + 图片引用 + citations |
| GET | `/api/conversations` | 会话列表（可选） | - | 会话列表 |

**统一响应结构**：`{ "code": 0, "message": "ok", "data": {...} }`；错误码区分参数错误 / 文件超限 / 服务内部错误 / Kafka 不可用等。

## 6. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 单文件解析（≤20 页）在正常负载下 2 分钟内完成；上传接口响应 < 2s（不含解析）；问答首 token < 5s |
| 并发 | Kafka 允许多个 Worker 分区级并行消费；问答接口支持并发调用 LLM |
| 可靠性 | 解析任务不丢失：消息持久化、手动 ack、失败重试；状态以数据库为准可恢复 |
| 安全 | 上传文件类型/大小校验；图片与文件访问做基本鉴权（作业场景可简化为登录态或免鉴权，需在实现说明中注明） |
| 可维护性 | 后端分层（API / Service / Worker）；解析逻辑与消息逻辑解耦，便于替换解析器 |
| 日志与监控 | 关键链路（上传、发消息、消费、解析、问答）均有结构化日志，含 task_id 便于追踪 |

## 8. 验收标准

1. **功能 1**：网页一次上传 ≥2 个 PDF，文件成功保存，Kafka 出现对应消息，Worker 完成解析，向量库与对象存储中可查到解析产物。
2. **功能 2**：上传后列表可见 `待解析` → `解析中` → `解析完成` 的状态流转；构造损坏 PDF 时能看到 `解析失败` 及原因。
3. **功能 3**：
   - 提问包含图片时，图片与问题一起进入 LLM（日志/Prompt 中可验证）；
   - 回答正确渲染为图文混排，图片可显示；
   - 回答附有来源（文档名）；
   - 上传一篇含图 PDF 后，针对图片内容提问能命中该图片并在回答中引用。

## 10. 开放问题（待确认）

1. **状态推送方式**：前端轮询即可满足需求，是否需要升级为 SSE/WebSocket 实时推送？
2. **图片检索策略**：图片召回依赖「图片描述生成」，是否启用多模态模型为每张图生成描述（增加解析耗时）？还是仅依赖图片周边文本？
3. **鉴权要求**：作业是否需要登录/用户隔离，还是单用户免鉴权？
4. **部署形态**：Docker Compose 一键部署还是手动部署？MinerU 对 GPU 的要求是否满足（无 GPU 时需使用 CPU 模式）？
5. **对话记忆**：多轮对话是否需要保留历史上下文参与检索与生成？
6. **文件保留策略**：解析失败/删除文档时，原件与产物是否需要级联清理？
