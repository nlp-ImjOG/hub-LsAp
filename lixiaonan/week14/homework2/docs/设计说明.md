# 系统设计说明

对应需求文档 `需求文档.md`（v1.0），F1-x / F2-x / F3-x 编号与之一一对应。

## 1. 总体架构

```
前端 (Vue3 + Element Plus + Vite)
   │  HTTP (multipart / SSE)
   ▼
后端 API (FastAPI, app/)  ──► MySQL / SQLite (文档·分块·会话元数据, §4)
   │ 保存原件                     ▲
   ▼                             │ 状态以数据库为准 (F2-3)
 Kafka topic: pdf-parse-task      │
   │                              │
   ▼                              │
解析 Worker (worker/, 独立进程) ───┘
   │ MinerU / PyMuPDF 解析 (F1-7)
   ├──► 向量库 FAISS / Qdrant（文本块 + 图片块向量, F1-8）
   ├──► 对象存储 本地磁盘 / MinIO（图片、Markdown 产物）
   └──► 关系库（分块记录、状态、耗时）
```

- **API 与 Worker 分进程**，通过 Kafka 解耦（削峰、可多实例并行消费分区）。
- 三条数据流与 §2.2 一致：上传链路、解析链路、问答链路。

## 2. 关键设计决策

### 2.1 消息可靠性（F1-5 / F1-6）

| 环节 | 方案 |
| --- | --- |
| 生产端 | `acks=all` + 等待 broker ack；发送失败任务置 `FAILED` 并提示用户（不丢上传） |
| 消费端 | `enable_auto_commit=False`，**处理成功才手动提交 offset**；崩溃后消息可重投 |
| 重试 | 解析异常 → `retry_count+1` 重新入队（指数退避，上限 `KAFKA_MAX_RETRY=3`）；耗尽置 `FAILED` 记录原因 |
| 消息体 | §3.1.3 结构（task_id / file_id / retry_count 等），Worker 按 `file_id` 回查数据库 |
| 超时兜底 | F2-4：Worker 周期检查停留超过 `STALE_PARSING_MINUTES`（默认 30）的 `PARSING` 任务，重新入队；二次超时置 `FAILED` 防死循环 |

### 2.2 状态机（F2-3）

`PENDING → PARSING → SUCCESS / FAILED`，**以数据库为唯一事实源**。Worker 先置
`PARSING`（记录 `parse_started_at` / 解析器名），成功置 `SUCCESS`（记录产物路径、页数、
耗时），失败置 `FAILED`（记录 `fail_reason`）。任何时刻进程崩溃都可从数据库恢复判断。
`POST /documents/{id}/reparse`（F2-5）仅允许 `FAILED` 任务重新入队。

### 2.3 解析器适配层（F1-7）

`worker/parser/base.py` 定义 `BaseParser.parse(pdf) -> ParseResult(markdown, images, page_count)`，
两个实现：

- **MinerUParser**：调用 `magic-pdf` CLI（`MINERU_CMD` 可整体覆盖），产出带版面分析的
  Markdown 与图片；重解析依赖（需 `pip install "mineru[core]"`）。
- **PyMuPDFParser**：无模型依赖的轻量实现（按页取文本 + 位图，过滤 <32px 装饰图），
  用于无 GPU / 未装 MinerU 环境的降级闭环验证。

Worker 消费时统一：图片落盘（`images/<doc_id>/<seq>.<ext>`）→ Markdown 中
`source_ref` 改写为可访问 URL → 分块 → 可选向量化 → 一次性写库（重解析幂等，先清旧块）。

### 2.4 分块与索引（F1-8 / F3-3）

- 分块（`worker/indexer/chunker.py`）：按 Markdown 标题/段落切分，`CHUNK_MIN/MAX_CHARS`
  控制粒度；图片引用行生成 `IMAGE` 类型块（记录 `image_url`、`page_no`）。
- 向量化（可选 `EMBEDDING_ENABLED`）：`BAAI/bge-small-zh-v1.5`（512 维）；
  **图片块的向量文本 = 可选的 LLM 图片描述 + 前后文本块上下文**（§7 开放问题 2 的取舍：
  默认开启描述生成，解析耗时增加但召回率显著更高）。
- 存储：`FaissVectorStore`（本地 `data/vector_store/`，IndexIDMap2，按文档删除支持幂等）；
  Qdrant 由同一适配层接口承载（`vector_store.py`），切换不需改上层。

### 2.5 检索与多模态问答（F3-1 ~ F3-8）

1. 检索（F3-3）：问题向量化 → FAISS Top-K（默认 5），支持 `document_ids` 过滤（F3-2）；
   向量依赖缺失或索引为空时**自动降级为关键词检索**（仅文本块）。
2. Prompt 组装（F3-4）：系统提示词 + 多轮历史（最近 6 条）+ 【参考资料】（文本块带
   `[资料n]（文档名 第x页）`、图片块带 `[图片n]（… URL: …）`）+ 用户问题。
   **召回图片与用户图片都转 data URL 内嵌**——云端 LLM 无法访问本地 `/static` 地址。
3. 输出（F3-5/F3-8）：SSE 事件流 `meta → status → chunk* → done(citations) → error?`，
   前端逐段渲染 Markdown（marked + DOMPurify），图片以 `/static` URL 正常显示。
4. 来源引用（F3-6）：`done` 事件与 `message.citations` 持久化
   （chunk_type / document_id / file_name / page_no / image_url / score）。
5. 思考模型适配：`glm-5.3-flash` 等思考模型正文与 reasoning 共享 `max_tokens`
   （需调大），流式转发仅取 `delta.content`、reasoning 增量自动跳过；
   `LLM_THINKING_EFFORT=low` 控制思考档位以降低首 token 延迟。

### 2.6 存储适配层（F1-3 / F1-8）

`LocalStorage`（`data/` 目录 + `/static` 暴露）与 `MinioStorage`（预签名 URL，7 天）
同一接口（save / read / exists / url_for），`.env` 的 `STORAGE_BACKEND` 一键切换。

## 3. 数据模型（§4）

- `document`：id、file_name、file_hash（SHA-256 判重 F1-9）、storage_path、size、
  status、fail_reason、page_count、parser_name、markdown_path、parse_started_at /
  parse_finished_at（耗时 = 二者差）。
- `chunk`：id、document_id、seq、chunk_type(TEXT/IMAGE)、content（图片块存周边上下文）、
  image_url、page_no、vector_id（= chunk id）。
- `conversation` / `message`：会话与消息（F3-7）；`message.image_urls`、`citations`
  存 JSON 字符串。

## 4. 已知边界与取舍

- SQLite 多进程写依赖 `busy_timeout=30s`，高并发建议切 MySQL（改 `DATABASE_URL`）。
- 关键词降级检索不含图片块（无向量时图片无法按语义召回），属可接受的降级形态。
- 统一响应 `{code, message, data}`；HTTP 状态码表达传输层语义，业务错误码见
  `app/core/exceptions.py`（1001 参数 / 1002 超限 / 1003 类型 / 1005 判重 / 2001 Kafka 等）。
- 鉴权：作业场景免鉴权（§6 允许，需注明）；生产部署建议加网关层登录态。
