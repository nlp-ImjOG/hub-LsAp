# 部署文档

## 1. 形态说明

| 形态 | 组件 | 适用 |
| --- | --- | --- |
| 生产/完整形态 | docker-compose（Kafka KRaft / MySQL / MinIO / Qdrant）+ MinerU | 交付演示 |
| 开发/沙箱形态 | 本机已有 Kafka + SQLite + 本地磁盘 + FAISS + PyMuPDF 降级解析 | 联调验证 |

两种形态共用同一套代码，差异全部由 `.env` 驱动（见 §3 配置表）。

## 2. 部署步骤（完整形态）

```bash
# 1) 基础设施
docker compose up -d          # kafka:9092 / mysql:3306 / minio:9000 / qdrant:6333

# 2) 后端依赖
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install "mineru[core]"    # MinerU 2.x；1.x 为 pip install "magic-pdf[full]"
                              # 无 GPU 也可运行（CPU 模式，速度较慢）

# 3) 配置与初始化
cp ../.env.example ../.env    # 按需修改（见 §3）
python ../scripts/init_kafka_topics.py
python ../scripts/init_db.py

# 4) 启动（三选一）
bash ../scripts/run_dev.sh    # 一键：init + API + Worker + 前端
# 或分进程：
uvicorn app.main:app --port 8000          # API（backend 目录下）
python -m worker.main                     # Worker（backend 目录下，可多实例）
cd ../frontend && npm run dev             # 前端 http://localhost:5173
```

生产部署将 `uvicorn` 换为 `uvicorn app.main:app --host 0.0.0.0 --workers N`（或
gunicorn+uvicorn worker），前端 `npm run build` 产物交 Nginx 托管并反代 `/api` 与
`/static`；Worker 多实例受 Kafka 分区数约束（每分区一个并发消费者）。

## 3. 关键配置（`.env`）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `DATABASE_URL` | `sqlite:///./data/homework2.db` | 生产切 MySQL：`mysql+pymysql://user:pass@host:3306/db?charset=utf8mb4` |
| `STORAGE_BACKEND` | `local` | `minio` 时需配置 `MINIO_*` 五项 |
| `PARSER_BACKEND` | `mineru` | 未装 MinerU 时用 `pymupdf` 降级（功能可用，无版面分析） |
| `KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092` | |
| `EMBEDDING_ENABLED` | `true` | 关闭后检索降级为关键词匹配 |
| `EMBEDDING_IMAGE_CAPTION` | `false` | 开启后解析时调用 LLM 生成图片描述（提升图片召回，增加解析耗时） |
| `LLM_BACKEND` | `mock` | `openai` = OpenAI 兼容协议真实调用 |
| `LLM_API_BASE` / `LLM_API_KEY` / `LLM_MODEL` | 智谱端点 / 空 / `glm-4.5v` | **必须为多模态模型**，否则图问不生效 |
| `LLM_MAX_TOKENS` | `2048` | 思考模型正文与 reasoning 共享额度，建议 ≥4096 |
| `LLM_THINKING_EFFORT` | `low` | 思考模型档位 `low/high/max`；非思考模型置空 |
| `MAX_UPLOAD_SIZE_MB` / `MAX_UPLOAD_COUNT` | 50 / 10 | 上传限制（F1-2） |
| `ALLOW_DUPLICATE` | `true` | `false` 时按 SHA-256 判重拒绝重复入库（F1-9） |
| `STALE_PARSING_MINUTES` | `30` | F2-4 超时兜底阈值，0=禁用 |

## 4. 验收自检（对应需求 §8）

1. **功能 1**：网页一次上传 ≥2 个 PDF → 列表出现 `待解析`；`kafka` 出现消息
   （`scripts/init_kafka_topics.py` 的 topic `pdf-parse-task`）；Worker 解析后
   `data/markdown/`、`data/images/`（或 MinIO bucket）出现产物，向量索引条目增加。
2. **功能 2**：列表状态流转 `待解析 → 解析中 → 解析完成`；上传一个损坏 PDF
   （如改后缀的文本文件、截断的 PDF）观察重试 3 次后 `解析失败` 并展示原因；
   失败任务可点「重新解析」。
3. **功能 3**：
   - 提问附带图片：回答中能描述该图片内容（日志 `data/logs/` 可核对请求含图片）；
   - 回答为图文混排 Markdown，资料图片以 `![...](/static/images/...)` 正常显示；
   - `done` 事件的 citations / 回答尾注包含来源文档名与页码；
   - 上传含图 PDF 后针对图片内容提问（如「示意图是什么颜色」）能命中
     `IMAGE` 块并在回答中引用该图。
4. **健康检查**：`GET /api/health` 返回 `kafka_ready=true`。

## 5. 常见问题

| 现象 | 处理 |
| --- | --- |
| 上传返回 `2001` | Kafka 未启动 / 地址不对；检查 `/api/health` |
| 任务卡在 `解析中` | Worker 未启动，或 **MinerU 本地引擎未启动**（`mineru server status` 检查；`run_dev.sh` 已自动拉起）；首次运行需下载模型（`MINERU_MODEL_SOURCE=modelscope`）；超过 `STALE_PARSING_MINUTES` 会自动兜底重新入队 |
| `解析失败: ... No ... engine available` | MinerU 本地引擎未就绪：`mineru server start` 后等 1~2 分钟（模型加载）；确认 `mineru config show` 中 `parse_server.local.mode=managed` |
| 引擎反复重启 / OOM | 内存不足：MinerU basic 档约需 2G、standard 档（1.2B VLM）约需 4G 专用内存；先停其他大内存进程，或降档 `mineru config set parse_server.local.managed_tier basic` |
| `Upload directory is already owned` | 有陈旧/并存的 mineru 引擎进程持有 `/workspace/.../.mineru-service.lock`：停掉多余 `mineru.parser.api_server` 进程或删除该锁文件 |
| `解析失败: mineru ...` | MinerU 未安装或模型未下载完成；临时切 `PARSER_BACKEND=pymupdf` 保闭环 |
| 图问回答不认识图片 | `LLM_MODEL` 不是多模态模型；换 `glm-4.5v` / `qwen2.5-vl-*` / `glm-5.3-flash` |
| 回答中途截断 | 思考模型耗尽 `LLM_MAX_TOKENS`，调大到 4096+ |
| SQLite `database is locked` | 已内置 30s busy timeout；高频并发建议切 MySQL |
| HuggingFace 模型下载慢 | 已默认 `HF_ENDPOINT=https://hf-mirror.com`；MinerU 权重走 `MINERU_MODEL_SOURCE=modelscope` |

> **MinerU 版本注意**：本项目按 MinerU **4.x** CLI 适配（`mineru parse` 子命令 + 本地 server 引擎 +
> `doc:` 库内图片引用）。若部署环境安装的是 2.x（`mineru<4`），用
> `MINERU_CMD="mineru -p {input} -o {output} -b pipeline"` 覆盖命令模板即可，解析器自动识别旧产物形态。
