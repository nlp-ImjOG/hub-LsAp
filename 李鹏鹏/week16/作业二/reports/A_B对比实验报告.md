# 给技能沉淀确定性脚本：一次 A/B 对照实验

> 对作业一的 `esg-monthly-report` 技能做两件事：
> ① 把"检索互联网 + 内容归集"里**有唯一正确答案**的部分沉淀成脚本；
> ② 用同一客户、同一统计期、同一模型，跑"无脚本"与"有脚本"两遍，量出差别。
>
> 全部结论可用 `data/metrics.json` 与本文末尾命令复现。

## 一、实验设计

| 项 | 内容 |
|---|---|
| 客户 | 中国神华能源股份有限公司（601088.SH / 01088.HK） |
| 统计期 | 2026-10-25 ~ 2026-11-24（背景窗 2026-08-26 起） |
| 方向 | 六方向：国内政策、国际规则、评级指数、行业、客户公司、对标企业 |
| 变量 | **只有"技能里有没有确定性脚本"这一项** |
| Arm A | 作业一的技能原样：SKILL.md 只讲流程与质量线，靠模型手工检索、手工建表、手工编号（渲染脚本除外） |
| Arm B | 作业二的技能：新增 `esg_source_pipeline.py`（plan/search/fetch/ledger/check）+ 两份数据文件（检索矩阵、权威度表） |
| 输入控制 | 国际规则/评级/行业三方向两者共用同一份语义检索结果，差别仅在之后的加工方式 |
| 判官 | 同一个 `check` 门禁与 `ab_metrics.py`，对两份产物用同一把尺子 |

Arm A 的技能原文保留在 `data/armA_original_skill/SKILL_no_script.md`，可直接 diff。

## 二、结果总表

|---|---|---|---|
| 来源规模 | 23 条 | 233 条候选 → 89 条入账 | 脚本不靠"注意力"决定收多少 |
| 报告引用编号 | 23 个 | 28 个 | |
| **引用未闭环** | **6 个** | **0 个** | A 有 26% 的引用指向不合格来源 |
| **引用合格率** | **73.9%** | **100%** | 核心差异 |
| 方向覆盖 | 6/6 | 6/6 | 打平，技能文字本身就讲清了要六方向 |
| 日期错误（模型声称 vs 页面实际） | 4/23 = **17.4%** | 4 处被**自动标记**并纠正 | 见第三节 |

| 门禁结论 | `exit=1`（1 个 ERROR） | `exit=0`（仅 WARN） | |

## 三、脚本真正改变的六件事

### 1. 引用闭环：73.9% → 100%

A 的 23 条来源里有 6 条经审计不合格，但它们在报告正文里被正常引用：

| 编号 | 问题 | 审计判定 |
|---|---|---|
| S03 | 中国钢铁新闻网 | T4 自媒体/聚合，不作引用来源 |
| S11 | 搜狐/鹰眼工作室 | T4，且为二手转述 MSCI 结果 |
| S18 | 财闻网 | T4，且与 S17 是同一事件 |
| S08 | 商务部答记者问（2026-01-01） | 距统计期末 297 天 |
| S15 | 能源局十五五规划原文（页面 2026-07-06） | 距统计期末 111 天 |
| S20 | 证券日报转述收购公告 | 与 S19 重复，被归并后无编号 |

这 6 条全部是"读起来没问题"的来源——它们有标题、有机构、有日期、有链接，五条质量线逐条检查也挑不出毛病。**只有把权威度分级和时效分档变成代码，"看起来合格"和"实际合格"才分得开。**

### 2. 日期：把 17.4% 的错误率从隐性变成显性

模型从检索结果里摘日期，23 条里错了 4 条：

| 模型写的 | 页面实际 | 差 | 影响 |
|---|---|---|---|
| 2026-11-11 | 2026-11-09 | 2 天 | 轻微 |
| 2026-06-29 | 2026-06-30 | 1 天 | 轻微 |
| 2026-08-10 | 2026-07-06 | 35 天 | 印发日 vs 发布日混淆，会误判时效 |
| **2026-11-01** | **2026-11-19** | **18 天** | **把 11-19 的事件写成 11-01，跨了报告截稿节奏** |

脚本按 `jsonld > meta > URL > 正文 > 接口` 逐级取证，并把出处记进 `date_source`；模型提供的日期与页面值不一致时记 `date_conflict`，一律以页面为准。B 的 89 条入账里，日期出处全部可查：`api 72`、`meta 9`、`body 6`、`url 1`、`jsonld 1`。

### 3. 去重：规则靠"跑出来的 bug"才写对

A 靠人眼合并了 1 组（S17/S18 神华运营数据），但漏了 S19/S20，导致 S20 成了悬空编号。

B 第一版只按标题相似度合并，实测立刻出错：**"…8月份主要运营数据公告"与"…10月份主要运营数据公告"标题几乎一样，却是两个事件**，被误合并成 1 条。最终规则是"标题二元组 Jaccard ≥ 0.72 **且发布日期相差 ≤ 10 天**"。

这条规则的价值不在于这一期省了多少事，而在于：**它一旦写进代码，之后每个月都生效**；手工作业时同类错误会每月重犯一次，而且没人会发现。

### 4. 权威度分级是一份可维护的数据文件

`references/tier-map.json` 把域名映射到 T1/T2/T3，未命中一律 T4（只作线索、不入引用账）。本期它挡掉了 **40 条 T4 自媒体/聚合**，其中就包括 A 引用的财闻网与搜狐。

实测中也暴露了这份表的缺口：中国经济网（`ce.cn`）、南方财经网（`sfccn.com`）一开始被判成 T4，导致"评级"方向入账为 0。把它们加进 T3 后恢复。**关键是修的是数据文件，不是代码。**

### 5. 可复现：同一输入，指纹一致

```
第一次台账指纹: d74a6044826d32bf（89 条）
第二次台账指纹: d74a6044826d32bf（89 条）
逐字节一致(忽略时间戳): True     重跑耗时 238.5s（命中缓存）
```

网络响应落盘缓存，二次运行零请求。A 的清单无法这样复核——它取决于当天模型注意到了什么。

### 6. 规模：候选池大 10 倍，报告只引 28 条

脚本用 34 条检索式、27 次查询收上 212 条候选，加上模型检索并入的 21 条，共 233 条；
归并成 226 起事件，89 条入账，报告最终引用 28 条。

**"多收、严筛、窄引"** 才是有余量的做法。手工时代候选规模受注意力约束，只能"边搜边定"，无法回头补。

## 四、脚本没有改变的（这四条比上面更重要）

### 1. 期外标注：5 : 5 打平

两臂都有 5 处引用超出统计期却没写"（背景）"。脚本能精确指出是哪几条、超窗多少天（A 最严重 53 天，B 44 天），**但"该写背景"这四个字只能由模型写**。

这条打平是诚实的结论：**门禁能发现纪律问题，不能替代纪律。**

### 2. 数字可溯源：20% → 46.7%，都不及格

根因是**表格型 PDF**：神华月度运营数据公告、季报主要指标表在抽文本时，"数字—单位"的对应关系被破坏（原文是列排列，抽出来是 `45.3427.241.1432.010.2(1.1)`），脚本的 `numbers` 字段对这些条目为空，于是人工核对过的正确数字（4,530 万吨、150.77 亿元）也被判"未命中"。

结论：**这条门禁目前只能当"抽查清单"，不能当结论。** 要真正解决，得引入带表格结构的 PDF 解析（如 pdfplumber 的 table 抽取），那是另一件事。

### 3. 相关性判断仍然归模型

B 的 89 条入账里，乐东气田批复、铁路科技创新规划、会计改革与发展规划都是关键词命中但**与神华无关**的条目。脚本按关键词与权威度收窄，**判断"与我客户有没有关系"必须留给模型**——所以台账是候选池，不是必引清单。

### 4. 语义检索仍靠模型

免密通用检索（必应 RSS）对中文政策类查询几乎不可用：查"生态环境部 碳市场 配额"返回的是百科词条与首页；且其 `pubDate` 是**抓取时间**而非发布时间，17 条候选因此全部无有效日期被剔除。

所以六方向里只有三个方向能纯脚本覆盖：

| 方向 | 通道 | 结果 |
|---|---|---|
| 国内政策与标准 | gov.cn 政策库 API + 生态环境部列表 | ✅ 纯脚本，59+12 条候选 |
| 客户公司 | 巨潮资讯公告 API | ✅ 纯脚本，23 条入账 |
| 对标企业 | 巨潮资讯公告 API | ✅ 纯脚本，46 条入账 |
| 国际规则 | 无免密入口 | ❌ 模型检索 + `--ingest` 归一化 |
| 评级指数 | 无免密入口 | ❌ 同上 |
| 行业层面 | 无免密入口 | ❌ 同上 |

**脚本替代的不是"搜索能力"，而是"搜索之后的归集与质检"。** 这是本次实验最重要的认识。

## 五、成本对照

| 项 | A 无脚本 | B 有脚本 |
|---|---|---|
| 检索 | 2 次语义检索（1 次被服务商限流中断） | 27 次结构化查询（34 条检索式）+ 1 次语义检索 |
| 抓取与抽取 | 模型逐个打开约 10 个页面 | 233 篇自动抓取抽取，冷启 446s，热跑 0s（缓存） |
| 填表 | 手填 23 行 × 5 字段（标题/日期/机构/编号/链接） | 手填 28 行 × 4 判断列（影响方向/量级/关系/动作） |
| 编号 | 手工 S01–S23，6 个悬空 | 自动编号，0 悬空 |
| 质检 | 无（靠自查） | 1 条命令，7 项门禁 |
| 指令预算 | SKILL.md 8,227 字节 | SKILL.md 10,504 字节 + 脚本 41,677 字节 + 2 份数据文件 3,701 字节 |
| 结果 | 读起来像样，但不可复核 | 读起来像样，且可复核、可重跑、可追责 |

**指令预算涨了约 5 倍**，换来的是"数字、日期、编号、权威度"这四类字段永不出错。这笔交易是否值得，取决于这份月报是给自己看还是要交付给客户、要经得起追问。

## 六、结论

1. **该沉淀成脚本的**：任何"有唯一正确答案"的步骤——检索式生成、结构化源采集、日期/机构抽取、去重、分级、编号、闭环校验。它们的共同特征是**错了不会报错，只会悄悄变错**。
2. **不该沉淀成脚本的**：相关性判断、影响量级、行动建议、写作。这些没有唯一答案，脚本化只会把错误藏得更深。
3. **脚本的最大收益不是省时间，是可审计**：A 的报告读起来和 B 一样像样；差别在"这段结论能不能被验证、下一期能不能以同样成本重做"。
4. **沉淀的粒度要选对**：检索式矩阵与权威度分级都是**数据文件**（JSON），改知识不改代码。这决定了这份技能明年还能用。
5. **门禁要分级**：引用闭环、日期出处、机构完整做成 ERROR（机器能判死）；期外标注、数字溯源做成 WARN（需要人判）。把需要人判的东西做成 ERROR，最后一定会被 `--skip-check` 绕过。

## 七、复现命令

```powershell
cd "作业二"
$env:PYTHONIOENCODING = "utf-8"
$py = "E:\software_data_center\conda_envs\py312\python.exe"
$S  = ".agents\skills\esg-monthly-report\scripts\esg_source_pipeline.py"

# ---- Arm B：有脚本 ----
& $py $S plan   --profile data\profile_shenhua.json --since 2026-10-25 --until 2026-11-24 --out data\plan.json
& $py $S search --plan data\plan.json --out data\hits.jsonl
& $py $S fetch  --hits data\hits.jsonl --out data\docs.jsonl
& $py $S fetch  --ingest data\raw_discovery.jsonl --out data\docs_semantic.jsonl
& $py $S ledger --docs data\docs.jsonl data\docs_semantic.jsonl `
      --since 2026-10-25 --until 2026-11-24 `
      --out data\armB\sources_B.json --cards data\armB\factcards_B.csv --md data\armB\ledger_B.md
& $py $S check  --ledger data\armB\sources_B.json --report "reports\B_有script_中国神华_ESG月报_2026-11.md"

# ---- Arm A：用同一把尺子审计手工产物 ----
& $py $S fetch  --ingest data\armA\ingest_A.jsonl --out data\armA\docs_A.jsonl
& $py $S ledger --docs data\armA\docs_A.jsonl --since 2026-10-25 --until 2026-11-24 --keep-ids `
      --out data\armA\audit_A.json --md data\armA\ledger_A.md
& $py $S check  --ledger data\armA\audit_A.json --report "reports\A_无script_中国神华_ESG月报_2026-11.md"

# ---- 对比指标 ----
& $py ab_metrics.py
```
