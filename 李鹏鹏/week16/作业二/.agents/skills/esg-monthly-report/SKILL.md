# ESG 月报生成技能

把"过去一个月的 ESG 信息噪声"压缩成"客户能直接上会的一份月报"。
核心不是罗列新闻，而是**替客户完成三件事**：判断哪些变化与他有关、影响有多大、下一步该做什么。

## 分工（本技能的核心设计）

| 谁做 | 做什么 | 为什么 |
|---|---|---|
| **脚本** | 检索计划、结构化信源采集、正文与元数据抽取、去重、时效分档、权威度分级、编号、门禁 | 这些工作有唯一正确答案，交给模型会漂移、会漏、会编 |
| **模型** | 语义检索（国际规则/评级/行业这三类没有结构化入口）、相关性判断、影响评估、行动建议、写作 | 这些工作没有唯一答案，脚本做不了 |

一句话：**脚本保证"找得到、记得准、编得对"，模型负责"看得出影响、写得出建议"。**

## 何时使用

- 需要按月为客户/本公司生成 ESG 简报、政策监测报告、行业动态月报
- 需要把零散的 ESG 新闻整理成有影响判断和行动建议的文件
- 需要做特定企业的 ESG 对标梳理（客户公司 vs 同业）

不适用：一次性深度专题研究、需要原报告的翻译。

## 硬性质量线

一份合格的月报必须满足以下五条，缺一条即不合格：

1. **时效**：所有引用条目落在统计期内；期外的重要背景需显式标注"（背景）"并注明原发布时间。
2. **可核验**：每条事实带来源机构 + 发布日期 + 链接，附录统一编号；无来源的判断写成"分析"而非"事实"。
3. **有关联**：每条信息都要回答"与客户有什么关系"，不得出现纯新闻搬运。
4. **有量化**：能落数字就落数字，避免"大幅""显著"等空词。
5. **可执行**：建议动作写到"做什么、谁来做、什么时候前完成"，不写"加强重视"这类废话。

第 1、2 条由脚本强制，第 3、4、5 条只能由模型保证。

## 流程

### 第 0 步：锁定参数

写一份 profile，后面所有命令都用它：

```json
{
  "client": "中国神华能源股份有限公司",
  "short": "中国神华",
  "code": "601088",
  "industry": "煤炭开采与洗选 / 煤电 / 煤化工",
  "peers": ["中煤能源", "陕西煤业", "兖矿能源"],
  "focus": ["甲烷", "CCUS", "范围三"]
}
```

统计期默认上月 25 日至本月 24 日。**背景窗自动取 since-60 天**（抓"上期发布、本期生效/截止"的政策）。

### 第 1 步：生成检索计划并采集

```bash
S=.agents/skills/esg-monthly-report/scripts/esg_source_pipeline.py

# 1) 检索计划：六方向 × 检索矩阵 -> 计划文件（纯函数，不联网）
python $S plan --profile profile.json --since 2026-10-25 --until 2026-11-24 --out plan.json

# 2) 结构化信源直采：gov.cn 政策库 / 生态环境部 / 巨潮公告 / 必应 RSS
python $S search --plan plan.json --out hits.jsonl

# 3) 抓正文并结构化：标题 / 机构 / 日期+日期来源 / 正文 / 数字证据 / 关键句
python $S fetch --hits hits.jsonl --out docs.jsonl
```

`search` 覆盖六方向中的**三个**有结构化入口的方向：

| 方向 | 通道 | 为什么可靠 |
|---|---|---|
| 国内政策与标准 | `gov.cn` 政策库 API + 生态环境部政策文件列表 | 官方接口，标题/机构/日期都在返回体里 |
| 客户公司 | 巨潮资讯公告 API | 官方披露渠道，标题含公告编号与事由 |
| 对标企业 | 巨潮资讯公告 API | 同上，按发行人过滤避免串号 |

**其余三个方向（国际规则、评级指数、行业层面）没有可用免密结构化入口**，必须由模型用语义检索找到 URL，再交给同一个管线归一化：

```bash
# 4) 把模型检索到的结构化结果并入同一台账（.jsonl 或 TSV，可多份）
python $S fetch --ingest model_found.jsonl --out docs_semantic.jsonl

# model_found.jsonl 每行字段：title / url / date / publisher / direction / note
```

> 实测结论：免密通用检索（必应 RSS）对中文政策类查询几乎不可用（会返回百科、问答与首页），且 `pubDate` 是抓取时间而非发布时间。它只能当"线索通道"，不能当引用来源。不要把报告建立在它上面。

### 第 2 步：建台账（去重 / 分档 / 编号 / 质检一次完成）

```bash
python $S ledger --docs docs.jsonl docs_semantic.jsonl \
    --since 2026-10-25 --until 2026-11-24 \
    --out sources.json --cards factcards.csv --md ledger.md
```

这一步做四件确定性的事，**不要绕过**：

1. **事件去重**：标题二元组 Jaccard ≥ 0.72 **且发布日期相差 ≤ 10 天**才合并。只靠标题会把"…8月份主要运营数据公告"和"…10月份主要运营数据公告"误合并成一个事件。
2. **时效分档**：`in_window` / `background_60d` / `stale` / `future` / `undated`。
3. **权威度分级**：按 `references/tier-map.json` 的域名表定 T1–T4；T4（自媒体/聚合）**不入引用账**，只留档作线索。
4. **编号**：只有同时满足"有日期 + 有来源机构 + 权威度 ≤ T3"的条目才拿到 `S01…` 编号。拿不到编号的条目不是被删除，而是进 `rejected` 并写明原因。

`factcards.csv` 是你真正要动的文件：确定性列已经填满，只留四列给你判断——
`影响方向【模型填】`、`影响量级【模型填】`、`与客户的关系【模型填】`、`建议动作【模型填】`。
如果 `factcards.csv` 里某条看起来与客户无关（关键词命中但主题无关，例如给煤炭客户的"铁路科技创新规划"），**不引用即可**，台账是候选池不是必引清单。

### 第 3 步：写影响评估（唯一必须由模型写足的部分）

对客户公司的每条动态，写足四层：

```text
【事件】本月发生了什么（客观、含数字）
【对 E/S/G 的影响】分别说明，只写有实际影响的面；无影响的面写"无直接影响"
【与监管/评级的连接】对应哪一条规则、哪个评级维度、哪个指标
【建议动作】动作 + 责任部门 + 时间节点 + 预期效果
```

引用编号一律用台账里的 `S**`，写作时直接写〔S12〕。没有台账编号的事实，写成"分析"。

### 第 4 步：渲染

```bash
python scripts/build_report.py report.md --html report.html --check
```

报告文末必须有来源表。`ledger --md` 的「来源清单」一节就是这张表，直接粘到报告附录即可：

```bash
# 生成台账（含可直接当附录的来源表）
python $S ledger ... --md ledger.md
# 把 ledger.md 的「## 来源清单」一节追加到报告的附录 C
```

引用写法：正文用〔S12〕或 [S12]，与来源表的编号对应。`build_report.py --check` 与
`esg_source_pipeline.py check` 都能识别这两种写法；`〔2026〕`这类中文文号不会被误判为引用。

### 第 5 步：过门禁（不合格就改，不要豁免）

```bash
python $S check --ledger sources.json --report report.md
# 加 --strict 可把 WARN 也当失败
```

| 门禁 | 级别 | 判定 |
|---|---|---|
| 六方向覆盖 | ERROR | 报告正文必须引用到全部六个方向 |
| 引用闭环 | ERROR | 报告引用的每个 `S**` 都必须在台账 `sources` 里 |
| 机构完整 | ERROR | 入账条目必须都有来源机构 |
| 日期来源 | ERROR | 入账条目必须记录日期来自 api/url/meta/body/jsonld 哪一级 |
| 占位符 | ERROR | 正文不得出现"（待补充）""TODO"等 |
| 期外标注 | WARN | `background_60d` 条目被引用时，上下文 160 字内要有"背景"字样 |
| 数字可溯源 | WARN | 报告里带单位的数字要能在来源正文/标题中找到（同量纲、容差 1%） |

**数字门禁为什么是 WARN 而不是 ERROR**：表格型 PDF（月度运营数据公告、季报主要指标表）抽出文本后"数字—单位"的对应关系会被破坏，脚本抽到的 `numbers` 为空，人工核对过的正确数字也会被判"未命中"。这类告警要人工确认，不能直接当错误。

## 已知边界（写报告时按此收窄结论）

1. **表格型 PDF 的数字不可自动抽取**：神华月度运营数据公告、季报主要指标表属此类。数字必须人工从原文核对，并在报告附录注明。
2. **免密通用检索质量不足**：国际规则/评级/行业三方向必须靠模型语义检索；脚本只做归一化。
3. **公告标题不能与正文日期混用**：脚本按 `date_source` 记录日期出处，模型提供的日期与页面抽取值不一致时会记 `date_conflict`。实测模型给的日期约 1/5 与页面不符，**一律以页面为准**。
4. **巨潮 `searchkey` 是全文匹配**：查"陕西煤业"会命中"陕西煤业化工集团"出资人发的别家公告。管线已按发行人（`secName`）二次过滤，自行改代码时不要去掉。
5. **`gov.cn` 政策库 `searchfield=title` 是严格 AND**：长词句命中为 0，管线同时跑标题模式与全文模式再按关键词收窄。

## 常见坑

- **把"征求意见稿"写成"已发布"**：务必区分 征求意见 / 发布 / 施行 / 截止 四个状态。
- **评级数字混用不同口径**：MSCI 字母档、S&P CSA 百分制、CDP A–F 档、中证 AAA–C。只看同体系内的同业相对位置。
- **只搜一个月会漏掉"上月发布、本月截止/施行"的节点**：`plan` 已自动带 60 天背景窗。
- **上市公司互动平台问答不可当事实引用**：只能作为"投资者关注点"。
- **行业对标只比结论不比口径**：同业"碳减排 X%"若边界不同（范围一/二 vs 含三），必须标注口径差异。
- **权威度表要维护**：`references/tier-map.json` 里没有的域名一律按 T4 处理（不入引用账）。发现正规媒体被误判为 T4，就把域名加进去——改数据文件，不改代码。
