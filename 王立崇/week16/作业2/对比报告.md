# 作业2：有确定性脚本的 Skill vs 无脚本的 Skill —— 效果对比

## 0. 结论先行

> **把「搜索互联网 + 内容总结」里确定性的部分沉淀成脚本，能显著提升 Skill 的确定性、可复现性、可靠性与成本可控性；
> 但「相关性判断、ESG 影响解读、文字成稿」这些模糊环节仍应交给 LLM。最优解是「确定性脚本打底 + LLM 做增量判断」的混合架构。**

本仓库两个 Skill 均采用该混合架构：`web_search.py`（多后端搜索）、`web_fetch.py`（正文抽取）、
`esg_bid_monitor.py` 里的金额归一化与聚合统计是**确定性代码**；`llm_summarize.py` 的结构化摘要 / 相关性筛选是**LLM 增量**。

---

## 1. 两种形态

| 形态 | 组成 | 搜索与总结由谁完成 |
| --- | --- | --- |
| A：有确定性脚本 | SKILL.md（说明/触发）+ 脚本（`esg_monthly_report.py` / `esg_bid_monitor.py`） | 脚本固定流水线；仅摘要与判断交 LLM |
| B：无任何脚本 | 只有 SKILL.md 提示词 | 模型自由发挥：自行规划关键词 → 逐条调搜索 → 临场总结成稿 |

---

## 2. 六维度对比

| 维度 | A：有确定性脚本 | B：无脚本（纯提示词） |
| --- | --- | --- |
| **确定性 / 可复现** | ✅ 高。固定关键词、固定解析、固定格式，两次运行字节级一致 | ❌ 低。检索词与行文每次不同，难以复现 |
| **覆盖面 / 不漏项** | ✅ 高。检索关键词模板 + 四章节结构写死在代码里，保证三类内容全覆盖 | ⚠️ 取决于模型当次规划，可能漏掉某章节或某关键词 |
| **可靠性与容错** | ✅ 高。搜索后端多级降级、正则兜底、异常回退到规则模式 | ⚠️ 低。易出现幻觉、编造来源、格式漂移、漏步骤 |
| **成本 / 时延** | ✅ 低。一次批量 LLM 摘要，其余是确定性的本地计算 | ❌ 高。多次「规划 + 搜索 + 决策 + 写作」LLM 轮次，token 与时延更高 |
| **可维护 / 可测试** | ✅ 高。函数可单测、可版本化、可审计 | ❌ 低。只能靠提示词调优，难回归测试 |
| **灵活性 / 泛化** | ⚠️ 中。新场景需改代码（但可用参数覆盖：`--company` / `--benchmarks` / `--days`） | ✅ 高。对新颖/模糊需求适应性强 |

---

## 3. 逐维度展开（结合本仓库实现）

### 3.1 确定性 —— 以「金额归一化」为例
`esg_bid_monitor.py::parse_amount` 用正则把 `元 / 万 / 万元 / 亿元` 统一换算成万元：

```python
_AMOUNT_RE = re.compile(r"([0-9][0-9,\.]*)\s*(亿元|万元|元|万)")
```

- **脚本**：`"1.2亿元"` → `12000.0` 万元，`"48万元"` → `48.0`，永远一致，聚合口径可控。
- **无脚本**：模型逐条心算换算，可能出现「1.2 亿元 ≈ 120 万」这类数量级错误，且两次运行结果不同。

### 3.2 覆盖面 —— 以「报告结构」为例
`esg_monthly_report.py` 把四类内容（政策/行业/公司/对标）与五章结构硬编码进 `build_report()`，
`render_section()` 保证每个章节都输出表格。对比实验（见 `对比实验.py`）用正则断言五个必需章节 100% 存在。
无脚本时，模型可能凭感觉组织，缺少「对标企业」或「风险建议」章节。

### 3.3 容错 —— 搜索后端多级降级
`web_search.py` 依次尝试 Serper → 博查 → DuckDuckGo → Bing，任一失败自动降级，全部失败返回空并让编排脚本进入规则模式。
这是「确定性脚本」才能稳定实现的容错；纯提示词模式下，模型遇到某工具报错往往会重试或放弃，行为不可控。

### 3.4 成本 —— LLM 调用次数
- **脚本**：一次 `summarize_documents` 批量摘要 + （可选）一次执行摘要，共 1~2 次 LLM 调用；
- **无脚本**：规划（1 次）+ 每次搜索决策与筛选（N 次）+ 最终成稿（1 次），典型 5~15 次 LLM 轮次，token 与延迟成倍上升。

## 4. 量化对比（可复现）

运行 `python 对比实验.py`（离线可跑脚本态，配置 LLM Key 后可跑无脚本态），会输出：

| 指标 | 有脚本 | 无脚本 |
| --- | --- | --- |
| 两次运行一致性 | ~100%（字节级一致） | 低（差异率通常 20%~60%） |
| 必需章节覆盖 | 100%（代码强制） | 60%~100%（取决于模型） |
| LLM 调用次数 | 1~2 次 | 5~15 次 |
| 端到端时延 | 秒级（本地流水线为主） | 数十秒到数分钟 |

---

## 5. 结论与最佳实践

1. **该脚本化的部分**：搜索关键词与后端降级、网页正文抽取、去重、金额归一化、聚合统计、报告章节骨架——这些「规则明确、可写死」的逻辑，脚本化后确定性、可复现、可测试、可审计。
2. **该留给 LLM 的部分**：相关性判断、ESG 影响解读、对标差距分析、自然语言成稿与建议——这些「模糊、需要判断与表达」的环节，LLM 明显优于规则。
3. **推荐落地形态**：`SKILL.md` 描述意图与触发 + 脚本承载确定性流水线 + LLM 做增量总结，即本仓库的混合架构。
4. **一句话**：**脚本负责「对不对、全不全、稳不稳」，LLM 负责「好不好、妙不妙」。**
