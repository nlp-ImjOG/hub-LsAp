## 1. 目标

用 Kafka 解耦"上传"与"解析"，实现一个可运行的多模态 RAG 问答系统：

| 编号 | 功能 | 验收标准 |
| --- | --- | --- |
| F1 | 前端一次上传多个 PDF，经 Kafka 异步交给后端，后端用 MinerU 解析并存储 | 多文件上传成功；解析产物（Markdown + 图片 + 元数据）落盘并入库；Kafka 有对应消息与消费记录 |
| F2 | 前端展示每个文件的解析状态：待解析 / 解析中 / 解析完成（补充：解析失败） | 状态在 ≤2s 内自动更新，无需刷新页面；失败可重试 |
| F3 | 多模态问答 | ① 回答支持图文混排；② 支持"文字 + 图片"一起送多模态 LLM 回答 |

## 3. 功能拆解与状态机

### 3.1 文档状态

```text
PENDING(待解析) --消费到消息--> PARSING(解析中) --成功--> COMPLETED(解析完成)
                                      |                        |
                                      +--失败--> FAILED(解析失败) --重试--> PENDING
```

- 状态落 SQLite，同时通过 SSE 广播给前端。
- 前端首次加载走 `GET /api/documents`，SSE 断线后兜底每 10s 轮询一次。
- 额外记录：`attempts`（重试次数）、`error`（失败原因）、`chunk_count`、`page_count`、`parsed_at`。

### 3.2 上传

- 多文件 drag & drop，单文件默认上限 50MB（⚠️ 可调）。
- 服务端按 `sha256` 去重（同文件重复上传直接返回已有记录）。
- 原始 PDF 存 `storage/uploads/{doc_id}.pdf`，便于前端预览与溯源。

### 3.3 解析（MinerU）

- 消费者调用：`mineru parse <pdf> -o <work>/doc.md --tier flash --json`。
  - `flash` 档本地可跑（实测 2 页 PDF 秒级），`basic/standard` 需启用本地 parse-server，本期不启用。
- 产物 Markdown 中的图片是**文档库定位符**：`![Image block](doc:450b881/tier:flash/page:1/block:8)`。
- 后处理：正则扫描定位符 → `mineru read "<locator>" --format image -o storage/parsed/{doc_id}/images/block_8.png` 导出真实图片 → 把 Markdown 链接改写为 `/static/parsed/{doc_id}/images/block_8.png`（该链路已实测通过，导出图为 PNG 1182×630）。
- 解析结果与图片统一放 `storage/parsed/{doc_id}/`，统计页数、chunk 数；MinerU 自身缓存位于其文档库（工具数据，不由本项目管理）。
- 失败重试 3 次（指数退避），仍失败则进死信 topic。

### 3.4 分块与入库

- 按 Markdown 标题层级切分，单块 ≤800 字，重叠 100 字。
- chunk 保留：`doc_id`、`chunk_id`、`content`、`page`（可推断时）、`images[]`（该块引用的图片相对路径）、`heading`。
- 每个 chunk 用 `embedding-3` 向量化（1024 维），写入 ES。
- 图片本身不做 embedding（本期只做"文本检索 + 图片随块带出"）。

### 3.5 问答

```text
用户输入(文字 + 可选图片)
   → 文本 embedding → ES: BM25 top20 + kNN top20 → RRF 融合 → top6 chunks
   → 组装 prompt（检索片段 + 图片引用说明）
   → GLM-4V（messages 内含用户图片）→ 流式输出 Markdown
   → 前端 markdown 渲染（图片走 /static 绝对路径）+ 右侧引用来源缩略图
```

- 图文混排约定：模型回答中的图片使用 Markdown 语法 `![描述](/static/parsed/{doc_id}/images/xxx.png)`；后端在 prompt 中提供可用图片清单，并做路径白名单校验，禁止外部 URL 混入。
- 图问：用户上传图片存 `storage/uploads/chat/{message_id}.png`，以 base64 或静态 URL 形式随消息送 GLM-4V。
- 每次回答保存 `sources_json`（命中的 chunk、doc、图片），供前端展示"依据"。

## 4. 系统架构

```text
┌───────────────┐   multipart    ┌──────────────────┐   produce    ┌─────────┐
│ React 前端    │ ─────────────> │ FastAPI (API)    │ ───────────> │  Kafka  │
│ 上传/状态/问答 │ <───────────── │  SQLite / 文件    │              │ pdf-parse│
└──────┬────────┘   SSE 状态     └────────┬─────────┘              └────┬────┘
       │                                   │                            │ consume
       │ SSE token                         │ 读写                       v
       │                          ┌────────┴─────────┐        ┌──────────────────┐
       └────────────────────────> │ Elasticsearch    │ <───── │ Parse Worker     │
                                  │ BM25 + dense_vec │        │ MinerU + 分块    │
                                  └──────────────────┘        │ + embedding      │
                                                              └──────────────────┘
```

- 进程组成（全部本机）：
  1. `kafka`（KRaft 单节点，9092）
  2. `elasticsearch`（9200，⚠️ 未安装）
  3. `uvicorn` 后端 API（8000，单 worker，内存事件总线 + SSE）
  4. `python -m app.workers.parse_worker`（可起 1~2 个消费者）
  5. `vite` 前端（5173）
- 说明：SSE 事件总线为进程内实现，因此 API 必须单 worker 运行；如需多 worker 需引入 Redis，本期不做。

## 6. 数据模型

### 6.1 SQLite

```sql
documents(id TEXT PK, filename TEXT, size INTEGER, sha256 TEXT UNIQUE, page_count INT,
          status TEXT, attempts INT, error TEXT, chunk_count INT,
          file_path TEXT, created_at TEXT, updated_at TEXT, parsed_at TEXT)

sessions(id TEXT PK, title TEXT, created_at TEXT, updated_at TEXT)

messages(id TEXT PK, session_id TEXT, role TEXT, content TEXT,
         images_json TEXT, sources_json TEXT, created_at TEXT)

chat_images(id TEXT PK, message_id TEXT, path TEXT, created_at TEXT)
```

### 6.2 Elasticsearch（索引 `rag_chunks_v1`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `doc_id` | keyword | 文档 ID |
| `chunk_id` | keyword | 块 ID |
| `content` | text（`cjk` analyzer，免插件） | 关键词召回 |
| `content_vector` | dense_vector(dims=1024, similarity=cosine) | 向量召回 |
| `page` | integer | 页码（可空） |
| `heading` | keyword | 所属标题 |
| `images` | keyword[] | 该块引用的图片路径 |

检索：BM25 top20 + kNN top20 → RRF(k=60) → 去重后取 top6 作为上下文。

## 7. 接口设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/documents` | 多文件上传，返回文档记录列表 |
| GET | `/api/documents` | 列表（可按状态过滤） |
| GET | `/api/documents/{id}` | 详情（含 chunk 数、错误信息） |
| POST | `/api/documents/{id}/reparse` | 重新解析（重置为 PENDING 并投递 Kafka） |
| DELETE | `/api/documents/{id}` | 删除文档及其分块、图片 |
| GET | `/api/events` | SSE：文档状态变更全局事件 |
| GET | `/api/sessions` | 会话列表 |
| POST | `/api/sessions` | 新建会话 |
| DELETE | `/api/sessions/{id}` | 删除会话 |
| GET | `/api/sessions/{id}/messages` | 历史消息 |
| POST | `/api/chat` | 问答，multipart(text + images[] + session_id)，返回 SSE token 流 |
| GET | `/static/*` | PDF、解析图片、聊天图片的静态访问 |

Kafka：
- topic `pdf-parse`（partitions=3，key=`doc_id`），消费者组 `pdf-parse-workers`
- 消息体：`{task_id, doc_id, file_path, filename, created_at}`
- `acks=all` + 幂等生产者；重试 3 次后投递 `pdf-parse-dlq`

## 9. 风险与阻塞项

1. ⚠️ **磁盘紧张**：清理后约 13 GB 可用，ES / MinerU 较占空间，演示建议用小 PDF。
2. ⚠️ **MinerU 只能跑 `flash` 档**：`basic/standard` 依赖本地 parse-server（默认 `mode=disabled`），质量与表格/公式识别弱于标准档，演示用小 PDF 即可。
3. **MinerU 文档库缓存在项目目录之外**（工具自身数据目录）；本项目只读取其导出的 Markdown/图片，不直接操作该缓存。
4. **GLM-4V 流式支持存在不确定性**：若 SDK 不支持 token 流，则降级为"按句切片伪流式"，SSE 协议不变。
5. **kafka-python 3.0.13 与 Kafka 4.4.0 的兼容性**需在 M1 用真实收发验证（含消费组、提交位点）。
6. **单进程 SSE**：API 只允许单 worker；多 worker 需 Redis，本期明确不做。
